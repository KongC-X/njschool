# 搜索可靠性诊断报告

> 诊断日期：2026-10-31　|　对象：`assets/search-core.js` + `site/assets/schools-data.js`（545 所全量数据）
> 方法：加载真实构建产物，在 Node 中跑全量自动化验证（非手写用例）

---

## 一、结论

**完整校名搜索是可靠的（100%），家长用的简称基本可用（93.9%），但有两类查询是坏的。**

三个问题，全部有代码级根因，全部可复现：

| # | 问题 | 实测 | 严重度 |
|---|---|---|---|
| 1 | **学段词搜不到**：`level` 字段不在搜索索引里 | 搜「初中」返回 **50** 条，实际 **164** 所；搜「初中 鼓楼」返回 **1** 条 | 🔴 高 |
| 2 | **排序对 73.9% 的学校系统性不利**：校名带「南京市」前缀的拿不到前缀分 | 搜「金陵中学」，本部排**第 5**，第一名是「金陵中学实验小学」 | 🟡 中 |
| 3 | **家长圈术语无覆盖，且兜底会误召回** | 搜「六大」返回 10 条无关学校（走简介匹配）；别名表仅 **7 条 / 覆盖 11 所（2.0%）** | 🟡 中 |

「六大」这类家长圈核心术语**完全没进别名表**，落到第三级「简介兜底匹配」，把所有 tagline 里出现「六大率」的学校都捞了出来——语义完全跑偏。

## 三、根因（代码级）

### Bug 1：`hayMain` 漏了 `level`

`assets/search-core.js:41`

```js
function hayMain(s) {
  return (s.name + ' ' + (s.short || '') + ' ' + s.type + ' '
          + (s.tier || '') + ' ' + s.district).toLowerCase();
  //                              ↑ 没有 s.level
}
```

`level` 只在 `passFilters()` 里用于**筛选**，不在 `match()` 的检索串里。

结果：**用学段筛选按钮能筛出来，在搜索框里打「初中」搜不到。** 同一份数据，两种行为不一致。

### Bug 2：`score()` 的校名前缀判定吃掉了「南京市」

`assets/search-core.js:88-95`

```js
if (name === t) total += 100;
else if (name.indexOf(t) === 0) total += 60;   // 前缀命中
else if (name.indexOf(t) !== -1) total += 40;  // 包含命中
```

- `"金陵中学实验小学".indexOf("金陵中学") === 0` → **60 分**
- `"南京市金陵中学".indexOf("金陵中学") === 5` → **40 分**

而 **403 所（73.9%）** 的校名以「南京市」开头。这批学校在搜索**任何**非全称关键词时，都稳定地比同族分校低 20 分。

同分时的 `name.length` 升序兜不住——20 分的差距已经决定了顺序。

### Bug 3：别名表设计正确，但内容是空的

`src/pipeline/aliases.py:25` 的机制是健全的（规范化后精确相等、候选必须命中真实学校否则构建失败）。但 `ALIASES` 只有 7 条，而南京家长的口语词远不止这些：

缺失的高频词（部分）：`南师附中`、`六大`、`金中`、`附中`、`四大名小`、`拉力琅芳`（有）、`树人`（靠简称）、`鼓实`、`求真`、`育英`、`玄外附小`…

其中「四大名小」能搜到是**运气**——因为 `tier` 字段里恰好写了「鼓楼四大名小（第一梯队）」。「六大」就不走运，因为它在 tagline 里而不是 tier 里，于是落进第三级兜底。

## 四、公平地说：已经做对的部分

不能只挑毛病。这套搜索在几个关键点上做得比多数同类站扎实：

| 做对的 | 价值 |
|---|---|
| 三级递进检索（主索引 → 地址 → 简介），只在上级零结果时降级 | 避免「二十九中」把只是提到它的学校也带出来 |
| 「九中」vs「二十九中」的子串边界判定（`hasTerm`） | 不用后行断言，兼容老 Safari |
| 组合别名整词比对（「拉力琅」不会带出芳草园） | 语义准确 |
| 阿拉伯数字归一（29中 → 第二十九中学） | 手机输入友好 |
| 地址层单独索引 + 结果卡写「施教区含：宁海路」 | 家长能判断为什么这条结果出现 |
| 构建期守卫：streets 与 schools 行数对齐校验 | 挡住「搜宁海路跳到别的学校」这类隐性错位 |
| 33 个纯函数单测，覆盖边界词 | `hasTerm` / `aliasHit` / `passFilters` 都有用例 |
| 545 份档案 **100% 含「数据缺口」章节** | 数据层的底子是硬的 |

**问题不在设计，在"设计对了但参数没校准"。** 三级检索、评分权重、别名机制的结构都是合理的，缺的是**数据驱动的验证**——现在的 33 个单测跑的是 `fixtures.json` 里 8 所手写样本，不是真实 545 所数据。

## 五、「怎么保证准确」——三层机制

这是问题的核心。搜索的准确性不能靠"我检查过了"，得靠三层独立的机制。

### 第 1 层：数据准确（源头，人工，一次性 + 增量）

| 现状 | 缺口 |
|---|---|
| 779 个核验项交叉复核（2026-10-17），A/B/C 信度标注，26 项存疑并列，545 份全含数据缺口清单 | **核验只覆盖 204 所（37%）**。10-24/25/26 新增的 341 所没有同等强度的核验记录 |

**这一层必须说清楚**：档案编写日期分布为 10-16（198 所）、10-17（6 所）、10-24（108 所）、10-25（197 所）、10-26（36 所）。核验报告对应的是前 204 所。后 341 所有没有做核验，从可查证据上看不出来——**这是需要确认的事，不是可以默认的事**。

**机制建议**：核验覆盖率作为可量化指标写进 `README` 和「数据说明」页；未核验档案在页面上显式标注（这符合本站"数据诚实"的一贯做法）。

### 第 2 层：索引准确（搜索层，自动化，可回归）

这是目前**最薄弱的一环**。`check.py` 的守卫覆盖了「格式没坏」，但没覆盖「功能是否有效」：

| 已有守卫 | 缺失守卫 |
|---|---|
| 行数对齐（streets vs schools） | 学段词召回率（搜「初中」是否 ≥ 160） |
| 列长度一致 | 完整校名 top1 命中率（应 100%） |
| 关键列非空 | 简称 top1 命中率（应 ≥ 90%） |
| JSON 合法 | 别名候选必须命中真实学校（`aliases.build` 已有，但没做成测试） |
| JS 无重复代码块 | 术语表覆盖率 |

**建议固化为 `tests/search-quality.test.mjs`**：加载真实构建产物，跑上面这批断言。跑不过就构建失败。

这样三个 bug 都会被自动挡住，而且以后每次改评分权重、加别名，都有回归保护。**这是"保证"的唯一可行形式**——不是承诺，是闸门。

### 第 3 层：结果可用（呈现层）

已有做得好的：命中高亮、命中来源标注、空态按「地址类/多词/筛选类」分类引导。

缺的一处：**同名跨学段结果不区分**。搜「仙外」返回两条「南京仙林外国语学校」，必须靠卡片上的学段徽章分辨。建议同名时在标题后加学段后缀（如「南京仙林外国语学校（初中）」）。

## 七、一句话回答

> **搜索在"你知道学校叫什么"的时候是可靠的（100%）；在"你只知道大家怎么称呼它"的时候，有一半可靠。**
>
> 而家长的真实输入几乎全部属于后者。

这个落差不需要重写搜索，需要的是：**把 7 条别名补到 40 条，把 `level` 加进索引，把前缀判定修好，然后用一套跑真实数据的测试把这三件事钉死。**

## A.3 一处判断修正（必须记录）

本报告 §2.4 把「别名表只有 7 条」列为 bug 3 的主因，并建议扩到 30–50 条。**这个判断不准确，修复时报废。**

实际验证发现：27 个候选口语词（南师附中、金中、鼓实、汇文、苏杰、明道……）**几乎全部已存在于 `short` 字段**，525 所（96.3%）都有简称。堆别名只会产生冗余。

真正的根因是评分档位缺一层：`short` 精确等于输入词时只给 **20 分**（简称包含档），而校名以该词开头给 **60 分**。于是「南师附中」本部（short 精确匹配，20 分）输给了「南师附中高淳学校」（校名前缀，60 分）。

修复方式相应改为**新增「简称精确 = 80 分」档**，而不是扩充别名表。别名只补了两条任何单校字段都无法表达的组合词（四大名小、四大名校）。

原报告该处结论已失效，以本节为准。

## A.4 刻意没做的两件事

**1. 「六大」「六大名校」不收进别名表。**
档案里它只作为升学指标（「六大名校达线率」）出现，108 处提及，但**从未列出是哪 6 所**。唯一一处能部分证实的表述是「含南师附中、金陵中学、二十九中、十三中『六大』中的 4 所」——只确认了 4 所，另外 2 所无据。按本项目「不以臆造数据填充」的原则不收，代之以在 `aliases.py` 里写明理由，避免以后被当成遗漏又补一遍。

**2. 没有改 README 的核验覆盖率。**
§5 提到的「核验仅覆盖 204 所（37%）」属实，但只能证明「核验报告对应 204 所」，**不能证明后 341 所没核验**——可能只是没写进那份报告。在确认之前不应单方面在公开文档里写「未核验」，这本身就不符合本站的数据诚实标准。此事待作者确认。
