# 南京中小学档案 · 站点重构方案

> 编制日期：2026-10-23　|　版本：v1.0　|　定位变更：数据副产品 → 长期运营站点
> 适用范围：`site/`（207 页）、`src/`（14 个脚本 / 4,703 行）、内容层（204 份档案）

---

## 一、现状分析

### 1.1 定位变化带来的要求差异

| 维度 | 作为「副产品」（现状） | 作为「长期运营站点」（目标） |
|---|---|---|
| 内容更新 | 一次性批量生成 | 每年招生季反复更新，需可追溯 diff |
| 正确性 | 生成时正确即可 | 错误可被及时发现并快速回溯修正 |
| 视觉 | 能用即可 | 品牌一致、多端一致、可持续扩展 |
| 协作 | 单人一次性 | 可能多人/多期接力，需降低理解成本 |
| 交付 | 本地目录 | 有域名、可索引、可分享、可监测 |
| 失败代价 | 重跑一次 | 家长看到错误信息 → 信任损失 |

### 1.2 量化基线

| 指标 | 现值 | 备注 |
|---|---|---|
| 页面数 / 总体积 | 207 页 / 7.2 MB | 6.73 MB 为 HTML |
| 详情页均值体积 | 33 KB | 最大 63.5 KB |
| 列表页体积 | 83 KB | 其中内联 JSON 约 56 KB |
| HTML / CSS / JS | 33 KB / 8.8 KB / 1.2 KB | CSS、JS 以字符串形式内嵌在 Python 源码里 |
| 生成代码 | 4,703 行 / 14 个脚本 | 单文件最大 714 行（含 CSS+JS+模板+业务逻辑） |
| 数据源 | 3 套 + 4 处硬编码 | md 档案、`index.json`、`school_websites.json`、政策表硬编码 |
| 同内容产物 | 3 份 | 根目录 `全景档案.html`、`site/index.html`、`site/schools.html` 高度重叠 |
| 版本控制 | **无** | 非 git 仓库 |
| 自动化 | **无** | 无 CI、无测试、无 lint、无部署流水线 |
| SEO 基础件 | 部分缺失 | 无 OG / canonical / JSON-LD；sitemap 含 207 个 `{BASE}` 未替换 |
| 可访问性 | 基础缺失 | 无 skip link / aria / focus 管理 / reduced-motion |

## 二、问题诊断

按「影响长期运营成本的程度」排序，而非按修复难度。

### P0 级：会直接阻碍长期运营

#### D1　信息架构：三份同源产物，无单一入口
根目录 `南京中小学全景档案.html`（单文件版）、`site/index.html` + `site/schools.html`（站点版）、`南京中小学档案.md`（目录版）内容高度重叠，且由**三个不同脚本**分别生成（`build_site.py` / `build_website.py` / `build_catalog.py`）。

- 后果：改一次视觉要改三处；三处必然漂移；对外难以说明「哪个才是官网」。
- 这是当前**最该先解决的问题**——它是后续所有重复劳动的根源。

#### D2　技术架构：生成器是单体脚本，无分层
`build_website.py` 一个文件里同时包含：设计令牌（CSS 字符串）、交互逻辑（JS 字符串）、页面模板（f-string）、业务规则（哪些区块显示什么）、硬编码内容（政策表、更名表）。目标架构应分为**内容层 / 数据层 / 呈现层 / 交付层**四层，当前全部压在一层。

#### D3　视觉：同一套样式被实现了三遍
`--bg:` 令牌定义出现 3 次（`build_website.py` 3 处、`build_site.py` 2 处、`build_html.py` 1 处）。三套 CSS 各自演化，已出现细微不一致（同一 `.card` 在不同产物里内边距/圆角不同）。**视觉一致性无法靠人工维持，必须收敛为单一令牌源。**

#### D4　内容：政策与更名数据硬编码在构建脚本里
「公办初中取消提前一年落户」「长幼随学」等内容分别出现在 `build_catalog.py`、`build_website.py`、`data_mid.py`、`data_policy.py` **四个文件**。政策是每年必变的高频内容，硬编码意味着每次更新都要改代码、且必然漏改其中一处。

#### D5　工程化：无版本控制、无 CI、无测试
- 无 git：无法回滚、无法 review、无法定位「哪次改动引入了错误」。
- 无 CI：部署靠手工，`{BASE}` 占位符这类缺陷能一路带到生产。
- 无测试：数据一致性目前靠手工 `grep` 抽查（本轮已多次依赖此方式发现跨文件残留）。

#### D6　交付缺陷：sitemap 不可用
`site/sitemap.xml` 含 **207 处 `{BASE}` 占位符**。以当前状态部署，搜索引擎拿到的是一份全站无效的 sitemap。这类问题在「有 CI 校验」的架构下不可能流出。

### P1 级：影响体验与迭代效率

| 编号 | 问题 | 说明 |
|---|---|---|
| D7 | 列表页内联 56 KB JSON | 首屏阻塞；应改为按需加载或分片，配合预加载 |
| D8 | 无全站检索 | 只有列表页前端筛选，无法跨页搜索「XX 政策」「XX 学区」 |
| D9 | 详情页无目录锚点 | 正文 33 KB / 11 个章节，家长想直接看「升学表现」只能滚动 |
| D10 | 表格窄屏体验差 | 横向滚动，未提供卡片化降级 |
| D11 | 筛选交互在移动端拥挤 | 11 个行政区 chip 换行 3 排，占据首屏 |
| D12 | 无 OG / canonical / JSON-LD | 分享到微信/群聊无卡片，搜索引擎收录弱 |
| D13 | 无空/错/加载态设计 | 仅有「无结果」一处空态 |
| D14 | 无打印样式 | 家长打印施教区/招生计划的场景未覆盖 |

### P2 级：细节与合规

| 编号 | 问题 |
|---|---|
| D15 | 无 skip link、无 `aria-*`、无 `focus-visible` 样式 |
| D16 | 未响应 `prefers-reduced-motion` |
| D17 | 正文标题层级依赖 CSS 隐藏 H1（`display:none`），对读屏不友好 |
| D18 | 无 `.gitignore` / `.editorconfig`，产物与源码混放 |
| D19 | 无数据 schema 校验，字段缺失靠 `KeyError` 运行时暴露 |
| D20 | 无监控（可用性、404、外链失效） |

## 三、重新设计的架构方案

### 3.1 信息架构（IA）v2

从「按物理属性罗列」改为「按家长任务组织」的三层结构：

```
L1 浏览（找到学校）
 ├─ 首页            定位说明 + 学段/区入口 + 本年度关键变化
 ├─ 学校库          检索 + 学段/区/性质/梯队多维筛选
 ├─ 学校详情        TOC 锚点 + 关键数据速览 + 十一节档案 + 官方渠道
 └─ 对比（新增）    2–4 所并排对比：本区定位/投档线/班型/官方渠道

L2 检索（找信息）
 ├─ 全站搜索（新增）  学校名/区/政策关键词，静态索引（Pagefind）
 └─ 标签页（新增）    民办摇号、施教区调整、更名、特长生

L3 解读（理解数据）
 ├─ 2026 政策（新增）  独立可引用页面，按主题分节，带来源与更新日期
 ├─ 更名与归属（迁移） 从首页表格提升为独立页
 └─ 数据说明           信度体系 / 数据缺口 / 官方渠道判定 / 更新记录
```

关键调整：

1. **首页减负**：现首页把政策表、更名表全塞进去，属于「内容仓库」。改为「任务入口 + 本年度变化摘要」，详情下沉到 L3。
2. **政策独立成栏**：政策是每年更新的高频内容，必须有独立 URL、独立更新日期、可被外部引用。
3. **新增对比页**：家长真实行为是「2–3 所之间比」，当前无此能力。
4. **详情页加 TOC**：11 节内容必须有锚点导航 + 回到顶部。

### 3.2 技术架构 v2：四层分离

```
┌─────────────────────────────────────────────────────────────┐
│ 内容层 content/                                              │
│   学校档案 *.md（front-matter 承载结构化字段）                │
│   页面内容 policy/*.md（政策、更名、说明，可独立编辑）         │
├─────────────────────────────────────────────────────────────┤
│ 数据层 data/                                                 │
│   schema.py（数据模型 + 校验）                                │
│   schools.json / websites.json（构建期产物，不入库）           │
├─────────────────────────────────────────────────────────────┤
│ 呈现层 templates/ + assets/                                   │
│   base.html / 组件片段（nav/card/table/badge/toc）             │
│   tokens.css（唯一样式源）/ app.js                            │
├─────────────────────────────────────────────────────────────┤
│ 构建 & 交付 build/ + .github/                                 │
│   validate → index → render → check → publish                │
└─────────────────────────────────────────────────────────────┘
```

#### 建议目录结构

```
南京学校/
├─ content/
│  ├─ schools/{小学,初中,高中}/{区}/{校名}.md      # front-matter + 正文
│  └─ pages/{policy-2026,renames,about}.md
├─ data/
│  ├─ schools.json            # 构建产物（不入库）
│  └─ websites.json           # 人工维护的官网核查结果（入库）
├─ build/
│  ├─ schema.py               # 数据模型与校验
│  ├─ load.py                 # 内容读取 → 结构化对象
│  ├─ render.py               # 模板渲染（Jinja2）
│  ├─ check.py                # 链接/结构/体积/SEO 校验
│  └─ main.py                 # 流水线编排
├─ templates/                 # Jinja2 模板与组件
├─ assets/
│  ├─ tokens.css              # 设计令牌（唯一来源）
│  ├─ base.css / components.css / pages.css
│  └─ app.js
├─ dist/                      # 构建产物（.gitignore）
├─ docs/                      # 方案、决策记录（ADR）
└─ .github/workflows/build.yml
```

#### 数据模型（关键改进）

现状：档案 md 里的结构化字段靠正文表格承载，构建时无法直接读取，只能靠 `index.json` 另存一份 → **两份真相**。

改造：md 顶部加 front-matter，结构化字段唯一存在于文件自身：

```yaml
---
name: 南京市琅琊路小学
short: 琅小
level: 小学
district: 鼓楼区
type: 公办
tier: 鼓楼四大名小（第一梯队）
founded: 1934
address: 琅琊路 7 号
feeder_junior: 南京市第二十九中学
website: http://lylxx.njgljy.com/
updated: 2026-10-17
---
```

`index.json` 降级为**构建期缓存**，不再人工维护；官网数据并入 front-matter 的 `website` / `wechat` 字段（或保留独立 `websites.json` 但由 schema 校验关联完整性）。

#### 技术选型对比

| 方案 | 优势 | 劣势 | 适用判断 |
|---|---|---|---|
| **A. 保留 Python，改为 Jinja2 + 模块化** | 沿用现有 4,700 行逻辑；团队零学习成本；数据校验用 Python 最顺手 | 前端能力有限（无热更新、无组件化 JS）；模板与资产需手工组织 | **推荐作为主线**（符合「不用框架」偏好） |
| B. Astro | 内容集合 + 类型校验 + 组件化 + 图片优化开箱可用 | 引入 Node 工具链与框架心智；现有 Python 数据处理逻辑需重写 | 若未来需要「多人内容协作 + 组件库」，作为演进方向 |
| C. 11ty | 轻量、模板语言灵活、纯静态 | 生态与类型检查弱于 A 的 Python 方案 | 备选 |

**结论**：主线走 A（立即获得收益、零迁移风险）；若 3–6 个月后出现「多人协作编辑 + 复杂交互组件」需求，再评估迁移 B，届时模板与数据模型已规范，迁移成本可控。

### 3.3 构建流水线与交付

```
validate（schema + 引用完整性）
   ↓
index（生成检索索引与分片数据）
   ↓
render（模板渲染 207 页）
   ↓
check（链接可达 / 结构性 SEO / 体积预算 / HTML 合法性）
   ↓
publish（GitHub Actions → Pages / Cloudflare，注入 BASE_URL）
```

配套要求：

1. **产物不入库**：`dist/` 进 `.gitignore`，用 CI 构建，仓库只存源码与内容。
2. **`BASE_URL` 由 CI 注入**，彻底消除 `{BASE}` 占位符问题。
3. **`check.py` 设硬阈值**：链接 404 = 失败；页面超体积预算 = 警告；缺 OG/canonical/唯一 H1 = 失败。
4. **数据校验前置**：必填字段、枚举值、官网 URL 格式、`website` 与 `websites.json` 的一致性，在构建第一环节拦截。

## 四、前端优化建议

### 4.1 设计令牌（单一来源 `tokens.css`）

现状色值/间距散落三套。建议建立 6 组令牌，所有样式只引用令牌：

| 组 | 建议值（示例） |
|---|---|
| 色彩 | `--c-bg` / `--c-surface` / `--c-text` / `--c-muted` / `--c-border` / `--c-accent` / `--c-accent-weak` / 语义色（成功/警示/危险） |
| 字号 | 模块化比例 1.2：12 / 14 / 16 / 19 / 23 / 28 / 34px，中文正文行高 1.75 |
| 间距 | 4 的倍数：4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 |
| 圆角 | `--r-sm 6` / `--r-md 10` / `--r-lg 14` |
| 层级 | 3 档阴影（卡片/浮层/抽屉），深色模式降为描边 |
| 动效 | `--t-fast 120ms` / `--t-base 200ms`，均受 `prefers-reduced-motion` 控制 |

### 4.2 布局与响应式

- **容器**：`--w-prose 68ch`（正文可读宽度）、`--w-wide 1180px`、`--w-full 1440px`。
- **断点**：`480 / 768 / 1024 / 1280`，采用「移动优先 + 单点增强」，避免多断点样式打架。
- **详情页改三栏**（≥1024px）：左侧 TOC 吸顶 + 中间正文 + 右侧关键数据卡；<1024px 折叠为顶部横向 TOC。
- **表格卡片化**：<768px 时 `data-label` 方案转成定义列表，替代当前横向滚动。
- **触控目标** ≥44×44px；移动端筛选改为「底部抽屉 + 已选条件条」，不再铺 3 行 chip。

### 4.3 视觉语言

| 要素 | 现状 | 建议 |
|---|---|---|
| 品牌标识 | 纯 emoji 🏫 | 设计简易字标（「南京中小学档案」+ 图标），SVG 内联，支持深色 |
| 信息层级 | 卡片、表格视觉权重接近 | 建立三级权重：主结论（大字号/强调色）＞辅助数据（常规）＞来源与信度（弱化灰） |
| 数据呈现 | 全部以表格承载 | 关键指标用「数字 + 单位 + 标签」的 stat 块；趋势用迷你条形 |
| 信度标注 | `[A]/[B]/[C]` 纯文字 | 语义色徽章（A 绿 / B 蓝 / C 橙）+ `title` 说明 + 图例 |
| 空/异常态 | 仅一处文案 | 统一样式：图标 + 一句话 + 明确下一步动作 |

### 4.4 可访问性（P2 但成本低，建议随 P1 一起做）

1. `<a class="skip" href="#main">跳到主要内容</a>`，聚焦时可见。
2. 所有交互元素 `:focus-visible` 描边；不使用 `outline:none`。
3. 筛选器改为 `<fieldset> + <legend>` 语义结构，chip 用 `role="checkbox"` 或真实 `<button aria-pressed>`。
4. 详情页正文不使用 `display:none` 隐藏 H1，改由模板只输出一个 H1。
5. 对比度：正文 ≥ 4.5:1，大字 ≥ 3:1（当前 `--muted` 在浅色背景约 3.9:1，需加深）。
6. 尊重 `prefers-reduced-motion`，关闭卡片位移与平滑滚动。

### 4.5 性能预算

| 指标 | 现状 | 目标 |
|---|---|---|
| 单页 HTML | 33 KB（均） | < 25 KB |
| 列表页 | 83 KB | < 40 KB（JSON 分片 + 首屏 40 条） |
| CSS | 8.8 KB 内联 | < 15 KB 外链 + 关键 CSS 内联 |
| JS | 1.2 KB 内联 | < 10 KB，`defer` |
| LCP（4G） | 未测 | < 1.5s |
| Lighthouse | 未测 | ≥ 95（性能/可访问性/最佳实践/SEO） |

### 4.6 SEO 与分享

1. 每页输出 `canonical`、`og:title/description/image`、`twitter:card`。
2. 详情页加 `JSON-LD`（`EducationalOrganization` + `BreadcrumbList`）。
3. sitemap 由 CI 注入 `BASE_URL` 生成，附 `lastmod`（取档案 `updated`）。
4. 生成 `robots.txt` 与 `404.html`。

## 五、落地优先级与迭代路径

优先级判定依据：**对长期运营成本的削减幅度** ÷ **改动成本**。

### P0（立即做，1–2 天）——止血

| 项 | 动作 | 影响 |
|---|---|---|
| 1 | `git init` + `.gitignore`（忽略 `dist/`、`site/`、`__pycache__`）+ 首次提交 | 获得回滚能力，是一切工程化的前提 |
| 2 | 修复 sitemap：`BASE_URL` 从环境变量注入，缺省时**不生成**而非留占位 | 消除上线即失效的缺陷 |
| 3 | 停用重复产物：`build_site.py` / `build_html.py` / `build_md.py` 归档到 `legacy/`，仅保留单一站点链路 | 消除三套并行维护 |
| 4 | CSS 抽取为 `assets/tokens.css` + `base.css`，三个生成脚本改为引用同一文件 | 视觉一致性的技术前提 |

### P1（1 周）——结构

| 项 | 动作 |
|---|---|
| 5 | `build_website.py` 拆分为 `load / render / check / main`，模板迁出为 Jinja2 |
| 6 | 引入 schema 校验（必填字段、枚举、URL 格式），失败即中断构建 |
| 7 | 数据收敛：官网数据并入统一数据模型；政策/更名内容从脚本移到 `content/pages/*.md` |
| 8 | 详情页加 TOC + 关键数据速览卡 |
| 9 | 补 a11y 基础件（skip link、focus-visible、aria-pressed、唯一 H1） |
| 10 | GitHub Actions：构建 + `check.py` + 部署 Pages |

### P2（2–4 周）——体验

| 项 | 动作 |
|---|---|
| 11 | 视觉系统落地：令牌应用、品牌字标、stat 块、信度徽章、空/错态 |
| 12 | 响应式重构：移动端筛选抽屉、表格卡片化、触控目标规范化 |
| 13 | 新增对比页（2–4 校并排） |
| 14 | 新增全站搜索（Pagefind 静态索引） |
| 15 | 政策页独立成栏，首页减负 |
| 16 | 性能优化：列表 JSON 分片、关键 CSS、图片/字体策略 |

### P3（持续）——运营

| 项 | 动作 |
|---|---|
| 17 | 数据监测：链接健康度定时体检（已有 `verify_websites.py`，接 CI 定时任务） |
| 18 | 内容更新流程化：招生季 checklist + 变更记录页 |
| 19 | 可选迁移 Astro（若出现多人协作/组件化需求） |

## 六、风险与取舍

| 风险 | 说明 | 应对 |
|---|---|---|
| front-matter 迁移成本 | 204 份档案需补结构化头部 | 写一次性迁移脚本，从现有表格解析生成；逐批校验，失败可回滚 |
| Python 生成器天花板 | 无组件化 JS、无热更新 | 当前站点交互简单，可接受；预留 Astro 迁移路径 |
| 过度设计 | 引入框架反而增加维护负担 | 严格遵守「四层分离」即可覆盖 90% 需求，不引入状态管理、不引入 SSR |
| 内容与代码耦合的回潮 | 后续新增政策可能又被写进脚本 | 在 `check.py` 中加入规则：构建脚本内出现政策正文关键词即告警 |
