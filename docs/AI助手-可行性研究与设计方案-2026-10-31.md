# AI 小助手 · 可行性研究与设计方案

> 编写日期：2026-10-31　|　状态：待评审，未实现
> 适用对象：南京中小学档案站（`site/`，纯静态，GitHub Pages）

---

## 〇、结论先行

**技术上完全可行，而且你这个项目的数据条件比市面上 90% 的 RAG 项目都好。但我建议放弃"做一个聊天框"这个形态。**

四个核心判断：

| # | 判断 | 依据 |
|---|---|---|
| 1 | **不该做通用聊天框，该做"带出处的问答"** | 你的护城河是信度、来源、数据缺口、冲突并列——这些是聊天框里最容易被丢掉的东西。通用 AI 输给你的不是"不会聊"，是"不知道自己在编"。把这些元数据显性化，才是把优势变成可见差异 |
| 2 | **P0 阶段不接 LLM，先做确定性问答** | 家长高频问题里约 6 成是"某校对口哪所初中""投档线多少""学费多少"这类有确定答案的。用结构化数据 + 模板答得更准、更快、零成本、零幻觉 |
| 3 | **检索放浏览器，生成放边缘函数** | 876 万字符塞不进任何 context；而 API Key 绝对不能出现在前端 JS 里 |
| 4 | **最大的风险不是技术，是托管位置和成本失控** | GitHub Pages 在国内的访问质量会直接毁掉体验；不限流的话，一个爬虫能一天烧掉你一个月预算 |

一句话总结方案：**前端先判断"这问题能不能用数据直接答"，能就直接出答案卡；不能才把 1–3 所学校的相关章节送去 LLM 组织语言，答案强制带出处和信度。**

## 一、这件事到底该不该做：产品层面的判断

### 1.1 你的担心是对的，但对手不是"AI"，是"AI 的自信"

家长的路径现在是：打开豆包 / DeepSeek / 元宝 → 问"南京琅琊路小学怎么样" → 拿到一段读起来很顺、但**无法验证**的回答。

问题不在"能不能答"，在**答错了家长也不知道**。而你自己的核验记录已经证明了这一点——README 里躺着多条实证：

| 第三方/AI 口径 | 实际情况 | 性质 |
|---|---|---|
| 育英外校"施教区范围 XX 路" | 民办校不存在施教区 | 判定为 AI 生成的错误信息，已排除 |
| 玄外 2025 摇号计划 202 个 | 权威媒体为 156 个 | 机构站错误数据，已判错 |
| 秦外摇号 240 个 / 郑外 160 个 | 112 个 / 90 个 | 同上 |
| 鼓楼实验中学地址 | 三个来源三个地址 | 至今存疑 |
| 金陵汇文"最高分 687" | 学校未确认 | 网传 |

**这就是你相对通用 AI 的绝对优势区：你不仅知道答案，还知道这个答案有多可信、哪里存疑、哪里没查到。**

所以 AI 助手的产品目标不该是"让家长少跳一次页面"，而应该是：

> **让家长第一次看到"一个敢标注自己不确定性的回答"。**

### 1.2 通用 AI 短期内补不上的三件事

| 能力 | 通用 AI | 你的档案库 |
|---|---|---|
| 施教区门牌号级覆盖 | 只能给"大概范围"，常编造 | 545 所逐校，源自区教育局公示原文 `[A]` |
| 冲突口径处理 | 挑一个说法讲，不告诉你还有另一说 | 20+ 条冲突项双口径并列，明确标注"待官方确认" |
| 数据缺口透明 | 不知道就说不知道（有时硬编） | 每份档案末节列明"未获取到的数据及原因" |
| 时效标注 | 常混用不同年份数据 | 每份档案标注数据截止月，逐年数据分列 |

第 2 条和第 3 条是**结构性优势**：通用 AI 没有动力去做，因为做了会让回答变丑、变长、变不确定。而你的整站价值观就是"数据诚实"。

### 1.3 反过来说，什么地方你不该做

| 不该做 | 原因 |
|---|---|
| 开放式"帮我推荐学校" | 义务教育阶段排名/推荐是敏感区，且必然滑向主观判断，一旦出错砸的是"准确"这块招牌 |
| 让 AI 生成档案正文 | 你已经用 10 个代理核验过 779 项，任何生成内容都是倒退 |
| 多轮闲聊 | 成本翻倍、跑题风险高、且不解决任何真实需求 |
| 替家长做决定 | 边界：提供事实和口径差异，不提供结论性建议 |

## 二、可行性基础：数据资产盘点

这一节回答"技术上凭什么能做"。结论：**你的数据是"模板化的半结构化知识库"，不是一堆散装 PDF，这决定了方案可以比通用 RAG 简单得多、准得多。**

### 2.1 规模实测

| 指标 | 实测值 | 备注 |
|---|---|---|
| 学校数 | **545 所** | 小学 340 / 初中 164 / 高中 41；公办 503 / 民办 42 |
| 正文字符总量 | **8,765,840 字符** | 平均 16,084 字符/所 |
| 章节块数（按 `##` 切） | **4,818 块** | 平均 8.8 块/所 |
| 章节块长度 | 中位 **642** 字，P90 1,489 字，最大 5,286 字 | **正好是 RAG 的理想粒度** |
| 详情页 | 545 个 HTML，站点总计 24MB | 单页 38–69KB |

⚠️ **注意**：`README.md` 里仍写着"204 所 / 240 万字符"，与当前实际严重不符，建议同步修正（不影响本方案，但会影响后续人力估算）。

### 2.2 已经具备的、别人没有的基础设施

这一项是可行性的关键——你**不需要从零搭 RAG**，因为已经有一半零件了：

| 已有资产 | 位置 | 在 AI 助手里承担什么 |
|---|---|---|
| 统一章节模板 | 小学 10 节 / 初中 11 节 / 高中 11 节 | **按章节检索**，而不是按固定字数硬切 |
| 校名别名表 | `src/pipeline/aliases.py` | 「拉力琅」「金中河西」这类合称/俗称的解析 |
| 数字归一 | `assets/search-core.js` 的 `cnNum` | 「29中」↔「第二十九中学」 |
| 地址/路名索引 | `site/assets/streets-data.js`（32KB） | 「我家住宁海路能上哪所」 |
| 结构化事实抽取 | `src/pipeline/facts.py` | 对口初中、投档线、学费、派位计划等 14 个字段 |
| 学校列表数据 | `site/assets/schools-data.js`（166KB） | 第一段检索的候选池，**已在前端** |
| 来源登记表 | `data/sources.csv` | 479 条带 URL 的来源，可直接做引用 |
| 官网/公众号核查 | `data/school_websites.json` | 「去哪看官方信息」 |
| 构建流水线 | `src/pipeline/` + `Makefile` | 检索索引可作为构建产物，跟站点一起发布 |

### 2.3 一个反直觉的结论：**不需要向量数据库**

理由是结构性的：

1. **数据是模板化的。** 每所学校的章节语义固定（速览 / 施教区 / 升学 / 师资 / 口碑 / 数据来源）。家长的提问类型也是有限的（约 8 类）。**问题类型和章节类型天然一一对应**，用一张手工映射表比 embedding 更准、更可解释。
2. **实体是封闭的。** 全部实体只有 545 所学校 + 11 个区 + 若干属性词。先定位实体（学校/区），范围就缩小到 1–3 所，剩下 8 个章节块塞进 context 毫无压力。
3. **向量检索解决的是"语义相似但用词不同"**，例如"作业多不多"→"家长口碑"。这类问题用 30–50 条口语映射表能覆盖 90%，而且**错了一眼能看出来**；embedding 错了你根本不知道为什么。

所以方案是：**实体定位（精确匹配）+ 章节映射（人工规则）+ BM25 兜底（bigram）**。三步都不需要向量。

后续若发现召回不够（例如大量"跨校比较型"问题），再考虑只对**章节标题+摘要**做向量（4,818 条 embedding，一次性成本几毛钱），而不是全量正文。

## 三、技术方案

### 3.1 四种架构选型对比

| 方案 | Key 安全 | 单次成本 | 首字延迟 | 复杂度 | 结论 |
|---|---|---|---|---|---|
| **A. 纯前端直连 LLM API** | ❌ Key 暴露在 JS，任何人 F12 就能拿走 | — | 低 | 极低 | **否决**（违反安全底线） |
| **B. 纯前端检索 + 模板回答（无 LLM）** | ✅ 无 Key | ¥0 | <100ms | 低 | ✅ **P0 采纳**，覆盖 6 成问题 |
| **C. 前端检索 + 边缘函数调 LLM** | ✅ Key 在服务端环境变量 | ≈0.006 元/次 | 1–3s | 中 | ✅ **P1 采纳**，主方案 |
| **D. 全后端 RAG 服务** | ✅ | 同上 + 服务器费 | 1–3s | 高 | 过度设计，暂不考虑 |

**推荐 C，并保留 B 作为降级路径**：边缘函数挂了，助手自动退回"结构化检索 + 直达链接"，功能降级但不白屏。

### 3.2 推荐架构数据流

```
用户提问
   │
   ├─① 前端意图解析（规则，0 成本）
   │    ├─ 抽实体：校名/别名 → 学校 ID；区名；年份；属性词
   │    └─ 判意图：8 类之一
   │
   ├─② 能确定性回答？
   │    ├─ 是 → 查 facts 索引 + schools-data → 渲染【答案卡】→ 结束（不走 LLM）
   │    └─ 否 ↓
   │
   ├─③ 取文：命中学校 1–3 所 × 相关章节 2–4 节（≈1,500–2,500 字）
   │        （正文按需从静态 JSON 分片加载，不预载全站）
   │
   ├─④ POST 到边缘函数 { question, schools, chunks[], intent }
   │        └─ 服务端：限流校验 → 拼系统提示 → 调 LLM → 返回带引用的结构化答案
   │
   └─⑤ 前端渲染：答案正文 + 引用块（学校/章节/信度/原文跳转）+ 免责提示
```

### 3.3 关键设计一：两段式检索（避免大索引）

| 段 | 输入 | 方法 | 数据源 | 体积 |
|---|---|---|---|---|
| 第一段：**定位** | 问题文本 | 别名表 + 数字归一 + 区名/属性过滤 | `schools-data.js`（已在前端） | 166KB |
| 第二段：**取文** | 学校 ID + 意图 | 章节映射表 → 按需加载该校章节 JSON | 新建 `chunks/<学校ID>.json` | 单校约 16KB |

**为什么这样设计**：
- 前端不需要加载 876 万字符，也不需要加载 4,818 块的全文索引
- 只有真正要问的那 1–3 所学校才去取正文，网络开销可控（3 × 16KB）
- `chunks/` 可作为构建产物与站点一起发布，走 CDN，无需额外服务

**代价**：多一次网络请求（约 100–200ms）。可以接受，因为可以在用户输入停顿时预取。

### 3.4 关键设计二：意图 → 章节映射表（核心资产）

这张表是整个方案里**最需要人工打磨**的部分，也是准确率的关键。示意（初版建议 40–60 条）：

| 家长的口语 | 意图 | 处理方式 | 取哪一节 |
|---|---|---|---|
| 「XX小学对口哪个初中」 | 对口关系 | **结构化直答** `facts.feeder` | — |
| 「我家住宁海路能上哪所」 | 施教区反查 | **结构化直答** `streets-data.js` | — |
| 「XX高中多少分能进」 | 投档线 | **结构化直答** `facts.score` | — |
| 「XX学费多少」 | 学费 | **结构化直答** `facts.tuition` | — |
| 「XX摇号多少人」 | 派位计划 | **结构化直答** `facts.lottery` | — |
| 「鼓楼区哪些小学好」 | 区域筛选 | **结构化直答** 按 tier 过滤 | — |
| 「XX和YY哪个好」 | 对比 | 跳转对比页 / 并列 facts | — |
| 「XX作业多不多 / 累不累 / 压力大」 | 体感 | LLM 组织 | 家长口碑 + 办学特色 |
| 「XX老师怎么样」 | 师资 | LLM 组织 | 师资力量 |
| 「XX有什么特色 / 社团」 | 特色 | LLM 组织 | 办学特色 |
| 「XX初中升学好不好的」 | 升学 | LLM 组织 | 升学表现 + 择校小结 |
| 「XX适合什么样的孩子」 | 综合 | LLM 组织（**加合规约束**） | 择校小结 + 口碑 |
| 「今年政策有什么变化」 | 政策 | 直答政策页 | `content/pages/policy-2026.md` |

**这张表的价值**：它把"语义检索"这个不确定的环节，变成了"可枚举、可测试、可回归验证"的规则。加一条规则就是一次明确的改进，而不是调参。

### 3.5 关键设计三：防幻觉靠数据结构，不靠提示词

这是全案最重要的工程判断。提示词约束（"不要编造"）在关键时刻几乎无效，真正有效的是**结构上不允许它编**：

| 手段 | 做法 | 效果 |
|---|---|---|
| **数字不走生成** | 投档线、学费、派位人数、班级数一律从 `facts` 填充模板，LLM 不参与 | 数字类错误率归零 |
| **只喂命中的章节** | context 里没有的学校，模型无法提及 | 天然阻止"张冠李戴" |
| **引用强绑定** | 每条结论必须挂 `[学校·章节]`，前端校验：回答里出现的学校必须在 context 内，否则重试或降级 | 无法引用即无法输出 |
| **冲突项显式并列** | context 中保留"两说并存"原文，提示词要求原样呈现为"口径 A / 口径 B" | 把最容易被抹平的差异保住 |
| **缺口显式说明** | 若该节含"数据缺口"，强制在答案末尾带出 | 用户看到"未收录"而非幻觉 |
| **拒答阈值** | 检索得分低于阈值 → 直接回"档案库未收录该校/该问题"，并给三条替代路径 | 宁可不答，不可错答 |

**建议的产品级表述**（写进 UI 而不是只写进提示词）：

> 本回答基于档案库 545 所学校的已核验内容，数据截止 2026-10。
> 标注 `[C]` 的内容为家长圈口径，需自行甄别；标"存疑"的项目档案中并列了两说。

### 3.6 关键设计四：答案卡的视觉结构

聊天框不该是唯一的输出形态。建议三种输出并用：

```
┌─────────────────────────────────────────────┐
│ 【直答卡】南京市琅琊路小学 → 对口初中          │
│  南京市第二十九中学初中部（单校直升口径）  [B] │
│  来源：档案 §6.1 对口初中 · 查看原文 →        │
│  ⚠ 口径提示：另有资料记为多校派位（档案并列）  │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ 【对比卡】琅小 vs 力学（12 项并排）            │
│  …（复用现有 compare 页逻辑）  [查看完整对比]  │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│ 【生成卡】「这两所的作业量差别」               │
│  正文（LLM 组织，2–4 句）                      │
│  ─────────────────────────────                │
│  依据：琅小 §8 家长口碑 [C]、力学 §8 家长口碑 [C]│
│  ⚠ 本节内容为家长圈口径，档案未获官方确认        │
└─────────────────────────────────────────────┘
```

**信度徽章 `[A]/[B]/[C]` 必须在答案里出现**。这不是装饰——它是你和通用 AI 之间唯一无法被抄走的东西。

## 四、成本估算

### 4.1 单次问答 token 拆解（生成卡场景）

| 组成 | 估算 | 说明 |
|---|---|---|
| 系统提示 | ≈400 字 | 角色、引用格式、拒答规则 |
| 检索章节 | 2,000 字 | 3 节 × 约 650 字 |
| 用户问题 + 少量历史 | ≈200 字 | 建议最多带 1 轮 |
| **输入合计** | **≈2,600 字 ≈ 1,800 token** | 中文按 ≈0.7 token/字 |
| 输出 | ≈400 字 ≈ 280 token | 限长，配合"要点式"输出 |
| **单次合计** | **≈2,100 token** | |

按国产主流模型当前定价量级（输入 1–2 元/百万 token、输出 4–8 元/百万 token）估算：

| 日提问量 | 日成本 | 月成本 |
|---|---:|---:|
| 100 次 | ≈0.6 元 | ≈18 元 |
| 300 次 | ≈1.8 元 | ≈54 元 |
| 1,000 次 | ≈6 元 | ≈180 元 |
| 5,000 次（异常） | ≈30 元 | ≈900 元 |

**结论：正常用量的成本可以忽略；真正的风险是被刷。** 必须配套：

| 措施 | 作用 |
|---|---|
| 边缘函数按 IP 限流（如 30 次/天） | 挡住爬虫和单人滥用 |
| 相同问题哈希缓存（24h） | 家长问题高度重复，缓存命中率预计 30–50% |
| 单次最大输入长度硬截断 | 防止有人塞长文烧 token |
| 每月硬性预算上限 + 告警 | 到线自动降级为方案 B |
| 前端不做"无限追问" | 最多 1 轮追问，之后引导回结构化入口 |

边缘函数的免费额度（Cloudflare Workers 10 万次/天等）在这个量级下完全够用，**这部分成本为零**。

## 五、风险清单

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | **API Key 泄露** | 🔴 高 | 绝不放前端；只用边缘函数环境变量；不在日志打印 |
| 2 | **成本失控（被刷）** | 🔴 高 | 限流 + 缓存 + 预算上限 + 降级 |
| 3 | **托管访问质量**（GitHub Pages 国内不稳定） | 🔴 高 | 见 §6 决策项；这是体验前提，不是优化项 |
| 4 | 幻觉/张冠李戴 | 🟡 中 | §3.5 六条结构性手段 |
| 5 | 合规（排名/推荐敏感） | 🟡 中 | 不做排名；不对义务教育阶段给绝对化建议；固定免责声明 |
| 6 | 隐私（家长可能输入孩子姓名/住址） | 🟡 中 | 输入侧不落库、不入日志；提示"请勿填写孩子姓名" |
| 7 | 政策时效（每年 5 月变） | 🟡 中 | 答案强制显示数据截止日；`policy-2026.md` 变更时重建索引 |
| 8 | 输入内容不当 | 🟡 中 | 输入侧关键词过滤 + 长度限制，超范围直接拒答 |
| 9 | 检索召回不足 | 🟢 低 | 先上线规则版，用真实提问日志（脱敏）持续补映射表 |
| 10 | 边检函数不可用 | 🟢 低 | 自动降级为方案 B（结构化检索），不白屏 |

## 六、实施路线（三阶段，建议按此顺序）

### P0 · 确定性问答层（不接 LLM）

**目标**：用现有结构化数据，把 6 成高频问题答准，零成本零幻觉。

| 交付物 | 说明 |
|---|---|
| `src/build_qindex.py` | 构建产物：`facts-index.json`（545 所 × 14 字段）+ `chunks/`（按校切片的章节 JSON） |
| `assets/qa-core.js` | 意图解析 + 实体抽取 + 模板渲染（纯函数，可 Node 单测） |
| 页面改造 | 学校库/详情页顶部加「问一句试试」输入框；详情页底部加「关于这所学校的常见问题」 |
| 3–5 条预设问题链 | 如"某校对口初中""某校投档线""我家住 X 路能上哪所" |

**验证标准**：
- 抽 30 条真实提问，意图识别准确率 ≥ 85%
- 对口初中/投档线/学费三类答案与档案原文 100% 一致（可自动化比对）
- `make test` 全绿，构建产物体积增量 < 500KB

**这一阶段就足以让家长感到"这个站比 AI 好用"**，因为它比 AI 快、比 AI 准，而且能点进原文。

### P1 · 生成层（接 LLM）

分两步，**先做小范围再做全局**：

| 步骤 | 形态 | 为什么这个顺序 |
|---|---|---|
| P1a | **详情页内嵌问答**「问这所学校」 | 上下文锁定 1 所，token 最省、准确率最高、风险最低。先在这里把提示词和引用机制调稳 |
| P1b | 全局问答入口（导航 + 首页） | 需要多校检索与歧义处理，复杂度高一个量级 |

**交付物**：
- 边缘函数（单文件，约 150 行）：限流 → 取 chunks → 拼提示 → 调模型 → 结构化返回
- 前端 `assets/chat.js`：输入 → 意图 → 取文 → 请求 → 渲染答案卡
- 缓存层（函数侧，可用 KV/内存）
- 降级开关：一个环境变量即可关掉生成、退回 P0

**验证标准**：
- 30 题基准集（见附录 A）准确率 ≥ 90%，其中数字类 100%
- 所有回答 100% 带可点击引用
- 无引用支撑的断言率 < 2%
- 单次 P95 延迟 < 5s（含首字）

### P2 · 增强（按数据反馈决定做不做）

| 项 | 触发条件 |
|---|---|
| 多轮追问 | 日志显示追问占比 > 20% |
| 向量召回（仅章节级） | 规则召回失败率 > 15% |
| 个性化（孩子年级 + 区 + 分数 → 候选） | P1 稳定运行 1 个月后 |
| 答案反馈按钮（有用/没用） | **建议 P1 就埋，成本极低**，是最有价值的数据 |

## 七、需要你决策的 4 个问题

### 1. 托管与访问（最优先，卡住一切）

站点在 GitHub Pages。**如果目标用户是国内家长，这个前置条件本身就需要重新评估**——一个要等 8 秒才加载出对话框的助手，不如不用。

三种选择：

| 选项 | 说明 | 代价 |
|---|---|---|
| A. 维持 GitHub Pages，只把 API 放国内边缘函数 | 页面慢但答案快，体验割裂 | 低成本试水 |
| B. 站点整体迁到国内可访问的静态托管（EdgeOne Pages / 阿里云 OSS / Vercel） | 体验完整 | 需域名（可能需备案） |
| C. 双轨：国内托管为主，GitHub 作镜像 | 最稳 | 构建需出两份 |

**我的建议是 B 或 C**，因为 AI 助手会放大"慢"这个问题：传统静态页慢一点还能忍（内容已在首屏），而问答是**空白等待**。

### 2. 模型选型

| 方向 | 优点 | 缺点 |
|---|---|---|
| 国产 API（DeepSeek / 通义 / 豆包） | 中文好、便宜、国内延迟低、合规明确 | 需自行做限流 |
| 边缘函数内置 AI（Workers AI 等） | 无 Key 管理、天然限流 | 中文能力和访问速度需实测 |

建议：**先用国产 API 做，抽象一层 `callModel()`**，切换成本控制在改一个配置。

### 3. 是否接受"拒答"

这是产品价值观问题，也是本方案的核心。**我强烈建议接受**：档案没收录的，直接说没收录并给替代路径。

代价是"问 10 个问题被拒 2 个"，收益是"剩下 8 个都能点进原文验证"。**这正是你和通用 AI 的分野**。如果为了"显得什么都会答"而放开，那这个助手就退化成一个更慢的通用 AI。

### 4. 商业定位

| 定位 | 影响设计 |
|---|---|
| 免费引流工具 | 强限流、答案卡带站内导流、缓存优先 |
| 会员增值（无限问 / 深度对比） | 需登录体系 → 必须引入后端与账号，复杂度跳一档 |

**建议先做免费引流**，验证真实需求后再谈会员。

## 八、一个必须做的额外动作：让外部 AI 引用你的出处

这一点比做站内助手更划算，且几乎零成本。

家长问通用 AI 时，AI 会去网上抓资料。如果你的档案以**结构化数据**形式暴露（`schema.org` 的 `FAQPage` / `EducationalOrganization` / `Dataset`），AI 在检索时就更容易抓到你的页面，并**在回答里带上你的来源**。

也就是说：与其只把家长拉到你的站内问答，不如同时让**所有 AI 在回答南京择校问题时引用你的数据**。这时候你的优势从"一个更好的搜索框"变成"这个领域的可信数据源"。

**动作**：详情页补 JSON-LD（`EducationalOrganization` + 关键属性），FAQ 型问题做成 `FAQPage` 标注。现有渲染层已有 JSON-LD 基础（README 提到 SEO 已做），扩展成本很低。

## 附录 A：建议先做的 30 题基准测试（1 天可完成）

在写任何代码之前，先做这个实验。它能用事实回答"我们到底比通用 AI 强多少"，也能直接产出 P0 的需求清单。

**方法**：
1. 收集 30 条真实家长提问（从家长群/论坛/自己熟悉的场景），覆盖 8 类意图
2. 每条问题分别用：① 通用 AI 直接问 ② 你的档案人工检索
3. 逐条判定：数值是否正确、口径是否注明、是否给出处、是否编造
4. 统计"通用 AI 答错/答不全"的比例

**预期结论**（待验证，不可先验宣称）：数值类问题通用 AI 错误率高，且**几乎从不标注不确定**；而"这学校怎么样"这类开放题，通用 AI 的语言组织反而更好。

**这个结论会直接决定产品形态**：如果是前者，就该做"精确问答 + 引用"；如果是后者，说明重点是"把档案讲得更像人话"，而不是做问答。

## 附录 B：不做什么（明确边界）

- ❌ 不做全站正文语义索引（4,818 块全量 embedding）——先证明规则召回不够
- ❌ 不做多轮长对话——最多 1 轮追问
- ❌ 不让 LLM 生成任何数字
- ❌ 不做学校排名/推荐结论
- ❌ 不在前端出现任何形式的 Key
- ❌ 不因为"AI 能答"就放宽数据核验标准——**档案仍是唯一真相源，AI 只是取用方式**
