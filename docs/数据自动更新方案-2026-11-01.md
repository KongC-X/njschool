# 数据持续获取与更新方案

> 适用对象：njschool.top（`KongC-X/njschool`）
> 编写依据：截至 2026-11-01 的仓库实测状态，非通用模板

---

## 一、核心业务目标

### 1.1 这套能力要解决的真问题

家长访问这个站的唯一理由是**拿它做判断**——查施教区、比投档线、看派位计划。判断出错代价极高（买错房、填错志愿），所以站的立身之本是数据诚实与新鲜。

当前的风险不是"数据少"，而是**数据会悄悄过期且无人知道**：

- 档案头部写着「数据截止 2026年10月」，但没有任何机制在 2027 年 5 月提醒你该更新了；
- `data/sources.csv` 登记了 1411 个来源标题，只有 **75 个（5.3%）**有 URL。剩下的 95% 事实——包括所有 `[A]` 官方口径——**无法回溯、无法复核、无法与自动抓取的结果比对**；
- `link-check.yml` 只探活，不探内容。学校官网改版、发布新招生简章，站上不会有任何信号；
- 2026-10 那次 779 项人工核验发现 37 个 P0 错误（"22 人"实为"220 人"、"1520"实为"1340"），全部靠人力穷举。这种做法不可持续，也不可复用。

### 1.2 目标（按优先级，可度量）

| 编号 | 目标 | 现状 | 目标值 |
|---|---|---|---|
| **G1 保鲜** | 官方口径变化后，白名单字段被识别的时延 | 不可控（人工季度检索） | 政策窗口期 ≤3 天，平峰 ≤7 天 |
| **G2 可追溯** | 白名单字段可回溯到「URL + 抓取时间 + 原文片段」的比例 | 约 5% | 100% |
| **G3 增量发现** | 新办/停招/更名/集团调整进入待办的时机 | 靠人事后想起 | 公告发布后 ≤7 天进待办 |
| **G4 成本** | 常驻运维成本 | — | 零服务器、月成本 ¥0、维护者每周 ≤1 小时 |

### 1.3 反目标（明确不做）

写清不做什么，比写清做什么更能约束范围：

- **不做全字段自动化**：口碑、办学特色、家长评价无法机读，强行抽取只会生产噪音。
- **不做实时抓取**：学校数据是年度周期，日更已是过度供给。
- **不做全站爬虫**：只盯列表页与已知附件，不镜像站点。
- **不做自动改写档案**：任何自动产出都只是"提议"，合并权在人。

## 二、现状盘点（基于代码实测）

| 能力 | 现状 | 评价 |
|---|---|---|
| 官网探活 | `src/verify_websites.py`：并发 10、三 UA 重试、抢注/停更/SPA/假 502 判定、`--apply` 写回、`--strict` 供 CI | **质量很高，可直接复用为采集层的健康判定** |
| 内容抽取 | `src/pipeline/facts.py`：从速览 KV 表抽取 14 个字段（含同义词表、缺口识别） | 证明"档案是可机读的"，但只用于渲染，未用于比对 |
| 来源登记 | `data/sources.csv` 2099 行；`sources_stats.json`：已核实 75、泛指 56、未存档 1280 | **最大结构缺口**：无 URL 锚点 |
| 校验闸门 | `schema.py`（字段/枚举/文件存在/数据缺口章节）+ `check.py`（产物检查） | 校验的是"结构对不对"，不校验"事实真不真" |
| 索引生成 | `build_index.py` 内 175KB 硬编码 `SCHOOLS` 列表 | 新增学校要改代码，天然双写风险 |
| 调度 | `build.yml`（push）、`link-check.yml`（周一 09:00） | 只有"发布"和"探活"，没有"采集" |
| 部署 | Actions 构建 → Cloudflare Pages（`--branch=master`） | 现成，无需改造 |

**两处已被数据打脸的细节**，说明缺的不是人力而是机制：

1. `README.md` 写「已完成 204 所」，而 `index.json` 的 `coverage` 是 **小学 340 / 初中 164 / 高中 41 = 545 份**。文档口径已滞后于数据本体。
2. `load.py` 注释记录：`counts` 缓存曾冻结在某天，导致 about 页把官网覆盖率从 34.5% 写成 28%。同一类问题——**派生数据没有重建机制就会腐烂**。

## 三、数据来源与获取方式

### 3.1 按「可机读性」分三层，不同层用不同手段

这是本方案的核心判断：**不存在一种统一抓取方式能覆盖全部数据源**，分层是必须的。

| 层 | 来源 | 典型载体 | 可机读性 | 获取方式 | 自动化级别 |
|---|---|---|---|---|---|
| **S1 强结构** | 市教育局、市招考院、11 个区教育局 | PDF 附件、固定表头 HTML 表格 | 高 | HTTP + `pdfplumber` + 表头模板匹配 | 全自动抽取 + 人审合并 |
| **S2 半结构** | 153 个可用学校官网 | 公告列表页、招生简章正文 | 中 | 列表页轮询 → 详情页按需抓 → LLM 结构化抽取 | 自动发现 + 人审合并 |
| **S3 弱结构** | 微信公众号、权威媒体、家长圈 | 推文、新闻稿、论坛 | 低 | **不硬爬**；人工投喂 + 关键词监测 | 人工主导 |

### 3.2 源清单要落成配置，不落成代码

新增 `data/sources.yaml`，把现有散落的知识（README 里那套域名规律、`school_websites.json` 的 153 条）固化为声明式配置：

```yaml
# 机构级源：年度窗口期高频
- id: edu-nanjing
  name: 南京市教育局
  kind: S1
  entry: https://edu.nanjing.gov.cn/
  list_selector: ".list a"          # 或 sitemap / RSS
  tier: T0
  parser: gov_attachment            # 命中附件即下载，按文件名分类

- id: njzk-bureau
  name: 南京市招考院
  kind: S1
  entry: https://www.njzb.net/
  tier: T0
  parser: score_table               # 投档线专用表头模板

# 区教育局：域名规律已在 README 记录，直接照抄，不要重新猜
- id: edu-gulou
  name: 鼓楼区教育局
  kind: S1
  entry: https://www.njgljy.com/
  tier: T0
  parser: gov_attachment
# 秦淮 njqhjy.net / 雨花台 yhjyxx.cn / 栖霞 *.site.qxteacher.com
# 江北 njnaedu.cn / 建邺 www.jyjsfz.cn/<学校代码>/ / 高淳 gcjy.info / 江宁 *.jnjy.net.cn

# 学校级源：由 school_websites.json 自动展开，只取 site_state=ok 的 153 条
- id: school:小学-鼓楼区-南京市琅琊路小学
  kind: S2
  entry: http://www.lylxx.cn/
  tier: T1
  parser: announcement_list
```

**为什么不把源写进 Python**：域名会变、站点会挂、学校会合并。配置改一行 vs 改代码走一次构建，成本差一个数量级。

### 3.3 抓取纪律（合规与稳定性，不可谈判）

1. **只抓公开页面**，不进登录态、不绕过验证码、不解析个人信息字段以外的内容。
2. 遵守 `robots.txt`：启动时先取一次并缓存 24 小时，`Disallow` 路径直接跳过。
3. 单域限速 **1 req/s**，并发上限 4（现有 `verify_websites.py` 是 10 并发，采集要更保守——体检只读一次首页，采集要读附件）。
4. UA 明确标注项目与联系方式（便于对方封禁前先联系）：
   `njschool-archive/1.0 (+https://njschool.top/about; contact@njschool.top)`
5. **微信公众号不做程序化抓取**。理由：无稳定公开接口、封号风险、抓取内容版权归属不清。公众号信息走 S3 人工通道，延迟 1–2 周可以接受。

## 四、更新频率与调度机制

### 4.1 按「信息半衰期」分档，不搞统一日更

南京的实际节奏是高度季节性的：5 月施教区与派位、6 月中高考、7 月投档线、9 月开学班级数、10–11 月新校与更名。**平峰期日更毫无收益，窗口期晚一天就是失职。**

| 档 | 对象 | 频率 | 窗口/理由 |
|---|---|---|---|
| **T0** | 市级 + 11 区教育局、招考院 | **每日 1 次**（仅 4/15–7/31、10/1–11/30） | 政策集中发布期 |
| **T0′** | 同上 | 每周 1 次（其余月份） | 平峰降频，省额度也省对方带宽 |
| **T1** | 153 个学校官网（公告列表） | 每周 1 次，周一 09:00 | 学校公告低频；复用现有 cron 时段 |
| **T2** | 全部官网可达性体检 | 每周 1 次 | 已有 `link-check.yml`，不动 |
| **T3** | 全量档案陈旧度、学校增减、更名巡检 | 每学期 1 次（2 月 / 9 月） | 结构性变化，非每日 |
| **T4** | 突发（临时更名、撤校） | `workflow_dispatch` 手动 | 兜底 |

### 4.2 调度落在现有 GitHub Actions，不引入调度服务器

```
.github/workflows/
├── build.yml          # 已有：push → 构建 → CF Pages
├── link-check.yml     # 已有：周一探活
└── data-watch.yml     # 新增：周一 05:00 采集 → 巡检 → 抽取 → 有新增则开 Issue
```

**✅ 2026-11-01 已落地** `data-watch.yml`（8 步）。三处按实际情况调整了原方案：

1. **没有做成 T0/T1 分档跑**。现有 188 个学校源以学校官网为主、公告频率低；13 个机构源里 12 个地址尚未核实。每日跑 188 个站点收益接近零，对区级平台的打扰却是实打实的。等机构源补齐后再分档——先跑通"每周一次"，再谈加密。
2. **不提交任何文件**。采集结果只进 artifact 与 Issue。自动提交会触发 `build.yml`，等于让未经核实的数字直接上线，与「人审是唯一写入口」冲突。代价是同一条新增会在基线提交前每周重复检出，用「已有未关闭 Issue 就不新建」兜住。
3. **告警用 Issue 而不是失败退出**。"发现新公告"不是错误，把它做成 CI 红会让人对红色脱敏；真正的错误（失败率 >20%）才让 workflow 失败。

本地能验证的部分都验了：YAML 合法性、shell 判断（无新增 / 有新增 / 失败率超限三种场景）、真实命令拼接出的报告格式能被 `grep` 正确识别。GitHub 侧的行为（cron 触发、Issue 创建、cache 命中）只能在首次真实运行时确认。

三个已知的 Actions 坑，方案里必须提前处理：

1. **定时任务会延迟**：高峰可延迟 30–60 分钟。对 T0 档可接受；不要用它做"准点发布"。
2. **60 天无提交自动停用**：加一条月度 keepalive（空 commit 或 `schedule` 心跳 issue），否则半年后整条链路静默死亡。
3. **免费额度**：公开仓库 Actions 免费；R2 存储有 10GB 免费额度，本项目快照远低于此。

### 4.3 一次 ingest 的执行顺序

```
载入 sources.yaml
  → 条件请求（ETag / If-Modified-Since），304 直接跳过（通常省掉 70%+ 请求）
  → 有变化才下载正文 + 附件 → 存 raw 快照（内容哈希寻址）
  → 按 parser 抽取为 facts（JSONL，带 source_url / fetched_at / span / confidence）
  → 与 md 现值 differ → 产 changeset
  → 开 PR（分支 ingest/YYYY-MM-DD），不自动合并
  → 汇总写 Issue（label: data-watch）
```

## 五、存储与缓存策略

### 5.1 四层存储，全部可丢弃可重建；只有一层进 Git

| 层 | 位置 | 生命周期 | 入库 | 说明 |
|---|---|---|---|---|
| **原始快照** | Cloudflare R2 `raw/<源id>/<sha256[:12]>.<ext>` | 有变化才留；全量 30 天 | 否 | 仓库已 61MB，快照入 Git 会迅速膨胀 |
| **HTTP 缓存** | `data/cache/http.json`（etag / last-modified / fetched_at / content_hash） | 长期 | 是 | 很小，但决定 70% 的请求能否跳过 |
| **抽取结果** | `data/facts/YYYY-MM.jsonl`（append-only） | 长期 | 是 | 纯文本，`git diff` 可读，可回放 |
| **变更集** | `data/changes/YYYY-MM-DD.json` | 90 天 | 是 | 一次 ingest 一份，含 run_id 与统计 |
| **派生索引** | `index.json` / `site/` | 构建期重建 | 否（已在 .gitignore） | 保持"可随时重建" |

### 5.2 为什么仍然不引入数据库

README 已经论证过静态优先，此处只在"持续更新"的语境下补充两点：

- **写入量极小**：白名单 6 个字段 × 545 所学校 × 每年 1–2 次变化 ≈ 每年几千行。用数据库解决这个量级的问题，换来的是运维成本与"不可 diff"。
- **Git 本身就是所需的一切**：版本、diff、回滚、审计、权限、PR 审核流，全部免费且已验证。

**升级触发条件**（写清楚，避免无限推迟）：当出现①按分数/施教区做在线多条件查询，或②小程序需要服务端筛选分页时，把 `facts/*.jsonl` 导入 SQLite 或云数据库即可，`facts` 的字段设计已按可直导设计。

### 5.3 站点侧缓存（现有架构不动，仅补一致性）

- `assets/schools-data.js` 已是外置数据资产（列表页 HTML 52KB → 12KB），构建时可按内容哈希命名，配长缓存头。
- Cloudflare Pages 自带 CDN；静态产物天然 immutable，无需额外配置。
- **唯一要求**：`index.json` 与 `schools-data.js` 必须由同一份 md 在同一构建内产出，禁止跨次构建混用（现 `build.yml` 已是单 job 内顺序执行，符合）。

## 六、异常与失败重试处理

### 6.1 分级处理（错误类型决定策略，不是一律重试）

| 类型 | 判据 | 处理 | 重试 |
|---|---|---|---|
| **瞬时** | 超时、5xx、429、连接重置 | 指数退避 1s → 4s → 16s，加 ±20% 抖动；429 优先读 `Retry-After` | 最多 3 次 |
| **永久** | 404 / 410、域名 NXDOMAIN、证书彻底失效 | 不重试，标 `dead`，进人工队列；沿用 `verify_websites.py` 的 `drop` 语义 | 0 次 |
| **语义异常** | 200 但正文无本校任何连续片段 / 命中抢注词 / 命中关停词 | 判「疑似抢注/空模板」，**不自动改任何数据**，只告警 | 0 次 |
| **假成功** | 200 但正文 <600 字节（纯 JS 渲染） | 判 `spa`，跳过抽取，不计失败 | 0 次 |
| **代理故障** | `Tunnel connection failed` / `Connection refused` | 判「未核实」，保留原记录。**这是已踩过的坑**：据此判死会误删大量正常站 | 1 次 |

后三条规则不是新设计，是把 `verify_websites.py` 里已经用血换来的判定**上移到采集层共用**，避免两套逻辑各错一次。

### 6.2 熔断：不熔断会反复打已死的站

单个域名连续 3 次 run 失败 → 该域静默 6 小时，状态写 `data/cache/circuit.json`。

现实依据：雨花台 `*.yhjyxx.cn` 是**整片平台停机（8 所）**，另有 28 所归为「源站下线」。没有熔断，每次 ingest 都会对这批站重复发起注定失败的请求——既是浪费，也是对已脆弱站点的持续骚扰。

### 6.3 局部失败不阻塞全局，但要可见

- 单源失败 → 该源标记 `degraded`，本次 run 继续。
- 构建期只拦「**新增**的永久失败」，已存在的失败不重复报错（否则 Issue 会天天重开）。
- 告警阈值：单次 run 失败源占比 >20%，或白名单字段抽取数环比下降 >30% → 升级为 Issue + 失败退出。

### 6.4 幂等

同一 `run_id`（= 日期 + sources.yaml 哈希 + 抽取器版本）重跑必须产出**逐字节相同**的 changeset。去重键：`source_id + content_hash + field`。

这条是为了让"重跑"成为安全的排查手段，而不是二次污染。

## 七、数据一致性保障

### 7.1 单一真相不变：md 是唯一真源

```
raw 快照 ──抽取──> facts.jsonl ──differ──> changeset ──人审──> md（唯一真相）
                                                     └──拒绝──> conflicts 表
```

自动化的任何产物都**不直接写 md**。人审合并后，现有 `build_index.py → build_website.py` 链路原样复用。

### 7.2 五道闸门

| 闸门 | 规则 | 解决什么 |
|---|---|---|
| **① 写入门禁** | 所有自动变更走 PR（`ingest/YYYY-MM-DD`），必须人审合并；合并后才触发 `build.yml` | 防止幻觉数据上线 |
| **② 溯源必填** | 新事实缺 `source_url` + `fetched_at` 时，**不得标 `[A]`**；只能标 `[C]` 或降级为待确认 | 打掉"无出处的官方口径" |
| **③ 量纲校验** | 投档线 450–760、招生计划 1–3000、班数 1–80、学费 0–200000 | 直接拦「22 人 / 220 人」「1520 / 1340」这类错误 |
| **④ 冲突留痕** | 与 md 现值冲突时不覆盖，进 `data/conflicts.csv`，**两说并列** | 延续现有做法，自动生成 README 那张冲突表 |
| **⑤ 构建期对账** | 扩展 `validate.py`：md 内引用的来源必须在 `sources.csv` 中且状态非「未存档」 | 让溯源率成为构建硬指标，而非口号 |

第 ⑤ 条要注意兼容现状——现在 1280 条是「未存档」，直接设为 error 会让构建永远失败。**分两步**：先对白名单 6 字段设为 error，其余设为 warning，随着锚点补齐再逐步扩大。

### 7.3 顺带解决 index 双写

`build_index.py` 里的 175KB `SCHOOLS` 硬编码列表是当前最大的结构性隐患：新增学校要改代码，而 `validate_counts` 只能事后发现不一致。

改造：把 `(校名, 简称, 区, 学段, 性质, 梯队, 一句话定位)` 迁到每份 md 的 YAML front-matter，`build_index.py` 退化为纯扫描器。

迁移用一次性脚本从现有 `SCHOOLS` 生成 front-matter，零信息损失；`schema.py` 增加「front-matter 必填字段」校验兜底。**这一步必须在自动新增学校之前完成**，否则自动化只能改代码，不能改数据。

**✅ 2026-11-01 已实施。** 落地过程中发现两处原方案未预见的问题，一并记录：

1. **顺序会丢**：索引顺序是「学段 → 梯队优先级 → 区 → 人工顺序」，最后一项此前靠「遍历 SCHOOLS + 排序稳定性」隐式兜底。改为扫描后实测 **406/545 个位置换位**。解法是把人工顺序显式写进档案的 `rank` 字段，而不是调排序规则——顺序是数据，不是代码。
2. **`strip_leading_h1` 会失效**：它遇到第一行 `---` 就 `break`，若 front-matter 未被剥离，详情页会出现**两个 H1** 且 YAML 直接显示在页面上。解法是把剥离做进 `source.text()` 这个唯一读取入口，10 处调用点自动安全。
3. **防误收**：删掉名单后，"放错区的文件"会静默进索引。补 `check_layout()`：front-matter 的 name/district/level 必须与文件路径三处吻合，不符即中断。

### P0 实施记录：采集层实测校正（2026-11-01）

原方案关于 S2「学校官网页 → 公告列表」的假设，被实测修正了三条：

| 实测发现 | 对方案的影响 |
|---|---|
| **平台空壳站**：鼓楼 `*.njgljy.com` 的学校首页是同一个 2084 字节框架页，两个不同学校返回内容**逐字节相同**，正文靠 JS 渲染 | 「抓学校官网首页」拿不到任何校方信息。S2 必须改为「入口页 → 发现公告列表页」，否则 188 个源里有一大批只能产出「同哈希」噪音 |
| **动态页面**：南师附小（87935B）、东山小学（253588B）每轮内容都变但字节数一字节不差 | 整页哈希比对对这类站天然失效。已在报告中单列「疑似动态」，根治要等 P1 的字段级比对 |
| **304 的真实语义**：`urllib` 把 304 归进 `HTTPError` | 若照搬异常语义，「内容未变」会被判成「抓取失败」——首轮全成功、第二轮有 ETag 就整批失败。已在 `_default_open` 单独处理 |
| **区教育局地址不可推测**：README 记的 `njgljy.com` 那批是学校官网托管平台，不是区教育局门户 | 11 个区教育局一律留空标 `unverified`，采集器跳过。宁可少抓，不可抓错——把托管平台当政策发布口，会把学校页面当成施教区公告 |
| **政府栏目页是 JS 跳转壳**：`/zb`、`/kb/` 都是 111 字节，只有 `htm="./gzzs/"; location.href=htm;` | 不跟随即把市教育局两个主栏目判成空壳，等于放弃最权威的源。已在 `fetch` 层实现跟随（含变量中转解析、无扩展名路径按目录处理、最多 2 跳） |

### P0 实施记录：列表页发现与条目比对（2026-11-01）

188 个学校源全量跑了一遍发现（200 次请求，约 3 分钟），结果：

| 结果 | 数量 | 说明 |
|---|---:|---|
| 找到可用列表页 | 125 | 其中 123 个首页本身即可抽条目，2 个需翻到栏目页 |
| JS 渲染壳 | 49 | 2084B 框架页（鼓楼平台）或 630B 壳（万网建站），HTTP 拿不到内容 |
| 未找到 | 14 | 首页为空或无匹配栏目 |

**这组数字修正了方案对 S2 的估计**：`school_websites.json` 标 `ok` 只说明「站点属于该校」，26% 的站内容根本抓不到。所以 `ok` 与「可采集」是两个问题，必须分开记录——现在 `source_lists.json` 的 `spa: true` 就是第二问的答案。

条目比对踩到的三个坑：

1. **首页轮播制造假新增**：按集合做差集，轮播转一次报 12 条「新增」。改为「从顶部往下走，遇到见过的就停」，只认顶部连续段。
2. **基线只存 8 条，比对却用全量**：导致列表 14 条时误报 12 条。两端口径必须一致。
3. **面包屑 `首页>> 通知公告` 混进基线**：9 个字恰好越过 8 字门槛。需按分隔符排除，且要先解 HTML 实体（`&gt;&gt;`）才认得出。

另一个必须补的基础设施：**304 时要有正文可用**。只存哈希的话，首轮抓完全部 304，`discover` 7/8 个源因拿不到 HTML 而失败。已实现内容寻址的 gzip 快照，304 时回填 body，快照缺失则自动重取一次。

### P1 实施记录：批次控制线抽取（2026-11-01）

**原方案对载体的假设是错的。** 方案写的是「PDF 附件 + 固定表头」，实测市教育局 2026-07-10 的分数线公告是**纯文字叙述**、零表格、6 张图片全是站点装饰：

> 普通高中指标生投档控制分数线为 593 分。
> 普通高中体育特长生投档控制分数线为 455 分，艺术特长生投档控制分数线为 490 分。

所以 `extract.py` 不引入 pdfplumber、不做 OCR、不做模板学习，改为「分句 + 取数字前最近类别锚点」。

**验收结果：抽到 7 项，与站点现值 7/7 一致**（593 / 560 / 490 / 455 / 535 / 535 / 500）。这不是抽取器自证，而是与站点已发布的 `templates/score.html` 交叉验证——两边独立得出同一个数。

抽错过的两个坑，都写进了测试：

1. **章节标题黏在正文前**：原文是「三、体育、艺术特长生 普通高中体育特长生投档控制分数线为 455 分」。按「句子含不含艺术」判断，这句含"艺术"也含"体育"，会把体育的 455 判成艺术。改为取**数字前最近的类别核心词**。
2. **核心词不能取整组词的最大位置**：「艺术特长生」与「体育特长生」共用「特长生」，按组取最大位置两者都落到同一个「特长生」上，区分度归零（实测都得到 17）。必须用规则首位的核心词。
3. **顿号不能当分句符**：「3+4 分段…、五年制高职与本科 5+2…」是并列的同一档，用顿号切开后后半段只剩「五年制高职」，会被误判成站点那行 385 分。同时给该规则加 `must_not=("与本科","5+2","3+4")`。

另一处必须记住的：**标题模式不能只认"投档控制分数线"**。栏目里有一篇「第二批次录取进程过半 在投档控制分数线上未被录取的考生…」，按关键词匹配会把它当发布页，抽出空结果。必须匹配"揭晓/公布/出炉"这类发布动作。

### P1 实施记录：派位计划抽取（2026-11-01）

**PDF 假设再次落空。** 已核实的 20 个施教区/派位文件里，**16 个是 HTML、仅 1 个 PDF**。鼓楼区派位办法页是 4 张标准 HTML 表格（其中 2 张是名单、1 张公文元信息、1 张页脚），抽取不需要任何 PDF 库。

做法：`htmltab.py` 只负责把 `<table>` 变成二维文本，判断留给抽取器——「表头同时含学校与计划」即名单表。这样元信息表（索引号/主题分类）与页脚自动排除，不依赖 DOM 结构。

**结果：抽到 10 所，与档案一致 7 所、数值不同 0、档案未记 0、校名对不上 3。**

校名匹配是本环节的真难点，两级策略：
1. 规范化（去空格、去「南京市」前缀）+ 缩写等价（`师范大学附属中学`↔`南师附中`）后**精确相等**
2. 否则**唯一子串包含**；多所命中一律判为对不上

第 2 步的严格性来自一个具体风险：「XX 小学」与「XX 小学某分校」一旦按包含放宽，分校的数字会被安到本部头上，而这种错在页面上看不出来。

**3 所对不上的经查是真缺档**：南京市鼓楼区第二实验小学（39 人）、南京市鼓楼实验小学（179 人）、南京鼓楼天河实验小学（34 人）。鼓楼区 27 所小学里没有任何一所含「实验」。报告不猜，给出「库中最相近校名」供人判断是写法差异还是该补档案——这正是 G3「增量发现」要产出的东西。

**补档后复验**：三所建档完成再跑同一任务，结果为「一致 10 / 数值不同 0 / 档案未记 0 / 校名对不上 0」。检测 → 补档 → 复验一致，闭环验证了这 3 份新档案的数字没错。

### P1 实施记录：施教区抽取（2026-11-01）

第三项也没有 PDF。鼓楼区政府「施教区是如何划分的」问答页是长文本，格式统一为 `校名：范围。`：

> 第二实验小学：东井村3号1-39幢，小市村1-29幢，小市村[1-100号（不分单双）]。

**按「校名：」的位置切分，不能按句号切**——范围文本里自带句号（「…（不分单双）。」），按句号会把一条拆成两条。

实测「…小学」在正文出现 50 次，其中只有 43 次是真条目，另 7 次是小节标题与行政语句（「一、鼓楼区主城小学施教区」「随着人口与学校布局」）。所以校名必须以「小学/学校/附小」收尾才算。

**这一项的产出不是校验，是缺档清单**：43 所里库内只能对上 26 所。

但**不能拿它当应收名单**。2023 年那份还含汉口路、回龙桥、察哈尔路三所，它们已经不在 2026 年招生办法的附件里（撤并）。用旧名单对账会凭空多出三个永远补不上的缺口——这正是前面反复出现的那个问题：**把历史数据当成当前事实**。

所以补跑了第四项：`school-list-2026-gulou`，从《鼓楼区 2026 年小学招生入学工作实施办法》的附件抽「校名 + 咨询电话」，46 所（含 1 所特教）。两版对照才得到确定结论：

| 依据 | 学校数 | 库内缺 |
|---|---:|---:|
| 2023 年施教区问答 | 43 | 17 |
| **2026 年招生办法附件** | **46** | **15** |
| 差异 | 3 所撤并（汉口路/回龙桥/察哈尔路）、3 所新增（滨江小学、金陵汇文小学部、力人学校小学部） | |

15 所待建：科睿、天妃宫、方兴、姜家园、树人学校附属小学、长平路、滨江、象山、民生实验、旭日景城、建宁、小市中心、五塘、砺志实验、力人学校小学部。

顺带修了校名匹配的两个缺陷：

1. **替换必须累积**：「南京财经大学附属小学」要先变「南京财经大学附小」、再变「财大附小」，单次替换对不上公告里的「财大附小」。
2. **起点要同时含原名与去前缀名**：单看去前缀形式，「南京大学附属丁家桥小学」会变成「大学附属丁家桥小学」，`南京大学→南大` 这条规则永远匹配不上。
3. **匹配必须限定学段**：「南京市金陵汇文学校小学部」拿去和全库匹配，会同时撞上同名的初中与小学档案，被判歧义而失败。名单本身限定学段，匹配也该限定（`load_schools(level="小学")`）。


### 附带修复：对账工具此前一直是坏的（2026-11-01）

把施教区结果接进 `reconcile.py` 时才发现，这个工具**从来没跑通过全部清单**：

- `check_file` 写死 `r["区"], r["学段"], r["学校"]`，而 17 份 `expected_*.csv` 只有栖霞那份是这种列名，其余 16 份直接 `KeyError`
- 也就是说「官方应收 vs 库内实有」的覆盖率从来没人算出来过

修法：列名按候选表取（`档案全称/学校/校名/名录名称/学校名称`），取不到再从文件名 `expected_{区}_{学段}.csv` 推断。

修完之后立刻暴露第二个问题：**口径错位**。

| 现象 | 数量 | 真实原因 |
|---|---:|---|
| 缺口 | 69 | 其中 65 所是「原江北新区 / 原浦口区」与档案「江北新区」不一致 |
| 缺口 | 6 | 4 所特殊教育学校（不在中小学档案范围）+ 1 所已停招（由分校代招）+ 1 所写法差异 |
| 缺口 | **0** | 加区名别名、`RESOLVED_WORDS`（停招/代招/并入）、`SKIP_WORDS`（特教类）与一条 `NAME_ALIAS` 之后 |

**最终：17 份人工清单 应收 422 / 已有 422 / 缺 0**（另 4 所特教不收录）。

这件事的教训写在这里：**「覆盖率 100%」这个结论，在工具坏着的时候也是 100%**——因为它根本没跑。指标要先证明自己算得对，再拿来做判断。

新增 `src/ingest/to_expected.py`（`make expected`）：把抽取到的施教区名单转成 `data/expected_gulou_primary.csv`。能对上档案的行写档案全称，对不上的写公告原名并由 reconcile 判「缺」——不替官方补全校名，所以鼓楼那份显示 43 应收 / 26 已有 / 17 待核实。

## 九、关键取舍

| # | 选择 | 放弃 | 理由 | 代价 |
|---|---|---|---|---|
| 1 | **人审合并** | 全自动写入 | 一次幻觉投档线，比缺 100 个字段更伤。站的立身之本是数据诚实 | 每周 30–60 分钟；用「白名单 + 置信度分层」压成本 |
| 2 | **Git + md 作真相** | 数据库 | 可 diff、可 revert、零运维、免费托管；写入量每年几千行 | 并发写与全文检索弱（当前不需要） |
| 3 | **定时拉取** | 实时/webhook | 源站不提供 webhook；日更已超需求 | 最坏 24 小时延迟 |
| 4 | **公众号人工投喂** | 程序化抓取 | 合规与稳定性；封号后连人工都做不了 | 公众号信息延迟 1–2 周 |
| 5 | **白名单 6 字段** | 全字段自动化 | 只有这 6 项错一次就误导决策：投档线、招生计划、派位计划、施教区、班级数、更名 | 覆盖面窄，口碑类仍需人工 |
| 6 | **准确率优先** | 覆盖率优先 | 与现有「未获取就写未获取」的做法一致 | 抽取数少，看起来"不够自动化" |
| 7 | **复用 Actions** | 自建调度/服务器 | 已有 CI 与部署链路，零边际成本 | 受 60 天停用与延迟限制 |

### 10.2 风险与对策

| 风险 | 可能性 | 对策 |

| 政府站加反爬/验证码 | 中 | 降级为人工，**不绕过**；记录到 sources.yaml 的 `manual: true` |
| LLM 抽取口径漂移 | 中 | 固定模型版本 + 37 项 P0 回归集 + 只提议不写入 |
| Actions 定时任务 60 天停用 | 高（易被忽略） | 月度 keepalive + 手动 dispatch 兜底 |
| 快照存储膨胀 | 低 | 只留有变化的版本 + 30 天全量清理 |
| 抓取行为引发投诉 | 低 | 限速 1 req/s、明确 UA、robots 优先、只抓公开页 |

## 十一、一句话总结

**这套方案的重点不是"抓得更多"，而是"让 545 份档案的每一个关键数字都能说清出处、都能在下一次官方口径变化时被及时提醒"。** 因此顺序必须是：先补溯源锚点，再谈自动抓取；先做变更提议，再谈自动合并。
