# 搜索与筛选：现状分析与优化方案

> 撰写日期：2026-10-26
> 对应代码：`templates/schools.js`（运行时）+ `src/pipeline/aliases.py` + `src/pipeline/render.py`（数据）
> 数据规模：545 所学校 / 11 个区 / 3 各学段
> 说明：你说的「这个功能」我按**搜索与筛选**来解——它是第一批刚重建的部分。若你指的是别的模块，说一声我重写。

---

## 0. 一句话结论

**现在的搜索能用了，但它是「一个能跑的函数」，还不是「一层可运营的检索能力」。**

第一批把召回从「搜不到」拉到了「常用说法能搜到」，但骨架仍是：**把字段拼成一个长字符串，然后 `indexOf`**。
这个骨架在 545 条数据上还能撑住，问题不在性能，而在**三个结构性缺口**：

1. **召回天花板低**：64% 的学校只能靠官方全名（的一部分）才能搜到，错一个字、打拼音、换个说法就 0 结果。
2. **逻辑不能复用也不能测试**：搜索逻辑长在页面内联脚本里，首页、404 页各自又写了一份跳转，三处入口三套实现，零测试。
3. **扩展一处要改四处**：加一个可搜索字段，得同时改 `hayMain` / `score` / `match` / 数据列，权重散在 if/else 里。

---

## 1. 现状：它到底做了什么

```
输入 → terms()：按空格切词 → 小写 → normTerm()（"29中"→"二十九中"）
     ↓
     两级索引：
       主索引 hayMain = name + short + type + tier + district（子串）
       兜底 hayExtra = tagline（仅当主索引 0 结果）
     ↓
     匹配：全部词命中（AND）；数字词「九中」做前字边界检查
     ↓
     评分：校名精确 100 / 前缀 60 / 包含 40 / 别名 30 / 简称 20 / 梯队区名 6
     ↓
     排序 → innerHTML 一次性重建全部结果卡片
```

实测基线与开销（Node 20，读构建产物里真实的 `schools.js`）：

| 指标 | 实测值 |
|---|---|
| 单次查询渲染耗时（JS） | 0.2 – 0.7 ms |
| `hayMain` 调用次数 / 次渲染 | 545（触发兜底时 1090） |
| 全量 545 张卡片 innerHTML | **331 KB**，约 4360 个元素 |
| 「琅琊路小学」9 次击键累计 | ≈ 2 ms |
| 有 `short` 简称 | 525 / 545（96%） |
| **`short` 只是全名子串**（不增加召回） | **331 / 525（63%）** |
| 有 `aliases` 别名 | 11 / 545（2%） |

⚠️ 最后两行是这一节最关键的发现：`short` 覆盖率 96% 看起来很高，但其中 **331 条的简称就是全名去掉「南京市」**（如「银城小学」→「银城小学」），搜索时本来就会被全名命中，等于没加召回。
**真正提供新信息的简称只有约 194 条，占 36%。加上别名 2%，约 62% 的学校只能靠官方全名的一部分被搜到。**

## 2. 不足之处

### 2.1 完整性（搜得到吗）

| # | 缺口 | 实测证据 | 影响 |
|---|---|---|---|
| C1 | **无拼音 / 首字母** | `langya` → 0 条，`lyl` → 0 条 | 手机上打「琅琊」「柘塘」「秣陵」「桠溪」这类字很痛苦，多数家长会试拼音。这是**最大的单一召回缺口** |
| C2 | **无容错** | `琅玡路` → 0，`郎琊路` → 0 | 形近字/同音字错一个就彻底搜不到，且没有「你是不是想搜」兜底 |
| C3 | **无「换一种说法」的桥接** | `二十九中初级中学` → 0（官方名是「第二十九中学初中部」） | 中文语序灵活，家长的说法和官方名之间没有映射层；别名表只解决了个案 |
| C4 | **无实时建议** | 输入过程中没有下拉 | 用户只能靠「匹配 N 所」这个数字猜，不知道系统「有没有这所学校」 |
| C5 | **无搜索历史 / 最近浏览** | 无 localStorage 记录 | 家长一次看 3–5 所学校，回来要重新输入 |
| C6 | **无结果排序切换** | 只有相关度一条路 | 想「这个区的都列出来按校名排」做不到 |
| C7 | **空态不说原因** | 只有「试试减少关键词」 | 不知道该删哪个词、哪条筛选（P2-3 已记录未做） |
| C8 | **别名沉淀不可持续** | 11 条写死在 Python 里 | 南京俗称几百个，靠开发者逐个加不现实；且改别名要动代码、要重新构建 |

### 2.2 健壮性（会不会出错）

| # | 隐患 | 说明 |
|---|---|---|
| R1 | **零测试** | 全部验证都是临时脚本（`/tmp/nj_h3.mjs`），不在仓库里。下次改搜索等于裸奔，第一批做对的东西没有任何护栏 |
| R2 | **三处搜索入口、三套实现** | 首页 `heroSearch()`（在 `app.js`）、404 页 `nfGo()`（内联）、学校库（完整逻辑）。前者只拼 URL，不做任何校验或提示 |
| R3 | **无防抖** | `input` 事件直接 `render()`，每次击键重建 |
| R4 | **未处理输入法合成** | 拼音未上屏时（`compositionstart` → `input` → `compositionend`）会用半截拼音过滤，结果闪烁、可能瞬间显示「0 所」 |
| R5 | **别名是隐式协议** | `aliases` 用**空格拼接**，`aliasHit` 用 `split(' ')` 还原。哪天出现含空格的别名（如「拉力琅 三校」）就静默断裂，没有任何校验 |
| R6 | **无输入边界** | 粘一段 1000 字进来 → 1000 个 term × 545 行；`0中` → `零中`（`cnNum(0)` 返回「零」）这类怪输入也无清理 |
| R7 | **数据列无一致性校验** | `cols` 与 `rows` 长度不匹配时，前端静默拿到 `undefined`，`hayMain` 拼出 `undefined`，表现是「某些学校永远搜不到」——这是最难查的一类 bug |
| R8 | **别名可能与校名冲突** | 若某条别名恰好是另一所学校的名字，那所学校会无条件出现在该别名结果里，构建期没有任何检查 |

### 2.3 可扩展性（改得动吗）

| # | 问题 | 后果 |
|---|---|---|
| E1 | **搜索逻辑长在模板里** | `templates/schools.js` 由 Jinja `include` 进 HTML，既不能 `import` 也不能单测，想复用到首页/404 只能复制 |
| E2 | **字段与权重硬编码** | 加「特色班型」为可搜索字段要改 4 处；权重 `100/60/40/30/20/6` 是魔法数字，没有配置 |
| E3 | **无索引构建阶段** | 索引是运行时从原始字段现拼。想换倒排索引、前缀树、bigram，没有插入点 |
| E4 | **别名表达能力有限** | 只能表达「别名 → 若干校名」，不能表达「别名 → 某个区」「别名 → 某一类」（如「民办初中」「九年一贯」） |
| E5 | **无结构化查询语法** | 「鼓楼区 九年一贯 公办」目前靠三词 AND 碰运气，不是真正的多面查询 |
| E6 | **索引源只有 index.json** | 档案正文里的章节标题（如「分班考」「直升」）不进索引，家长搜这类词只能靠 tagline 兜底 |

## 3. 实测后决定「不改」的几项（避免过度优化）

写这份分析时我原本准备了几条，实测后发现**不值得做**，列出来避免后续白花力气：

| 曾经想改 | 实测结论 |
|---|---|
| **预计算 haystack 提速** | `hayMain` 每次渲染 545 次字符串拼接，总耗时 **0.2 ms**。预计算能省 0.1 ms，不值得引入缓存失效的复杂度 |
| **上倒排索引 / 前缀树** | 545 条线性扫描 0.2 ms。倒排索引在这个量级上是纯负债（构建 + 内存 + 调试成本） |
| **引入 lunr.js / Fuse.js** | 体积 20–40 KB，为 545 条数据引入一个全文检索引擎，属于杀鸡用牛刀；而且中文分词它们做得并不好 |
| **全文索引档案正文** | 正文 20 MB。索引它会让首屏从 197 KB 涨到几 MB，与「极快」的定位冲突。要索引也只索引**章节标题**（不到 5 KB） |

**真正的性能瓶颈不在 JS，在 DOM**：全量 545 张卡片是 331 KB 字符串 / 4360 个元素，浏览器解析 + 重排的成本比 JS 高两个数量级。这条属于 P0-1，与搜索逻辑无关。

## 4. 可改进方向

```
            ┌─────────────────────────────────────────────┐
   召回     │ 拼音 · 首字母 · 容错 · 说法桥接 · 章节标题    │  ← 决定「搜不搜得到」
            └─────────────────────────────────────────────┘
            ┌─────────────────────────────────────────────┐
   交互     │ 建议下拉 · 防抖 · IME · 分页 · 空态 · 历史     │  ← 决定「用起来顺不顺」
            └─────────────────────────────────────────────┘
            ┌─────────────────────────────────────────────┐
   工程     │ 独立模块 · 字段配置 · 测试 · 别名外置 · 守卫  │  ← 决定「改不改得动」
            └─────────────────────────────────────────────┘
```

**优先级判断**：工程层先行。
理由：召回和交互的改动都会反复迭代，如果逻辑还锁在模板里、还没有测试，每一次迭代都在裸奔，第二批改完的东西第三批就可能被改回去。**先把地基和护栏立起来，再往上加功能。**

## 5. 具体优化方案

### 5.1 架构：把「检索」从「页面」里剥出来

现在是一个 148 行的内联脚本，什么都干。拆成三层、两个文件：

```
assets/search.js        （约 200 行，无 DOM 依赖，可单测）
  ├── CONFIG      字段与权重
  ├── normalize() 查询归一：全半角 / 大小写 / 阿拉伯数字 / 拼音识别
  ├── buildIndex()构建期预计算一次（含拼音、首字母）
  └── query()     匹配 + 评分 + 兜底 + 建议，返回 {items, total, mode, suggestion}

assets/search-ui.js     （约 120 行，只碰 DOM）
  ├── 输入框：防抖 / IME / 建议下拉 / 键盘上下选
  ├── 结果区：分页渲染 / 骨架屏 / 空态
  └── 状态：写回 URL / 恢复历史
```

**关键约束**：`search.js` 里**不允许出现 `document`**。这样它可以在 Node 里被 `node --test` 直接测，也能被首页、404 页、对比页复用。首页和 404 页的 `heroSearch()` / `nfGo()` 全部删掉，改为调用同一份 `search.js`。

### 5.2 索引层：字段与权重变成配置

```js
// assets/search.js
const FIELDS = [
  { key: 'name',     weight: 100, match: 'sub' },      // 校名
  { key: 'short',    weight: 45,  match: 'sub' },      // 简称（琅小、金中）
  { key: 'aliases',  weight: 40,  match: 'exact' },    // 俗称（整词，见 5.3）
  { key: 'pyFull',   weight: 35,  match: 'sub' },      // 全拼 langyalu
  { key: 'pyInit',   weight: 30,  match: 'exact' },    // 首字母 lyl
  { key: 'type',     weight: 10,  match: 'exact' },    // 公办/民办
  { key: 'district', weight: 9,   match: 'sub' },      // 鼓楼
  { key: 'tier',     weight: 8,   match: 'sub' },      // 梯队
  { key: 'tagline',  weight: 2,   match: 'sub', fallback: true },  // 仅兜底
];
```

加一个可搜索字段 = 往数组里加一行。权重不再是 if/else 里的魔法数字，而是可调的配置。

**拼音怎么来（不引入运行期依赖）**

方案：**一次性生成、永久内置**。
1. 写 `src/gen_pinyin_map.py`，用 `pypinyin` 把校名里出现的所有汉字转成「全拼 + 首字母」，产出 `data/pinyin_map.json`（约 600 字，30 KB 以内）。
2. `pypinyin` **只在这一个生成脚本里用**，产物入库；构建流水线只读 JSON，不依赖 `pypinyin`。

**必须处理多音字。**南京地名是重灾区，`pypinyin` 的默认读音会错：

| 词 | 默认易错读法 | 南京本地读法 | 说明 |
|---|---|---|---|
| 六合 | liù hé | **lù hé** | 区名 |
| 栖霞 | xī xiá | **qī xiá** | 区名 |
| 秣陵 | mò líng ✓ | mò líng | 一般正确 |
| 汤山 | tāng shān | tāng shān | 一般正确 |
| 淳化 | chún huà | chún huà | 一般正确 |

做法：`data/pinyin_map.json` 之上再加一份 `data/pinyin_override.json`，按**整词**覆盖（`{"六合":"luhe","栖霞":"qixia"}`），生成时优先查整词表。整词表需要对着南京本地读法人工核一遍——这几十条是整个拼音方案里唯一需要人工的部分。

### 5.3 查询层：四项具体改进

**① 拼音与首字母**
```
输入 langyalu / langya / ly l / lyl  →  命中「南京市琅琊路小学」
```
规则：`/^[a-z]{2,}$/` 才走拼音通道；`pyInit` 用整词相等，`pyFull` 用前缀，避免 `lj` 命中一大片。

**② 容错（只在零结果时启用，且必须标注）**
```
第一轮：精确（现状逻辑）
第二轮（0 结果才跑）：每个词允许 1 处编辑距离，且词长 ≥ 3
第三轮（仍 0）：tagline 兜底（现状已有）
```
界面上必须写「**找不到「琅玡路」，已显示近似结果**」，否则用户会以为「琅玡路小学真的存在」。——这一点与你一贯的「不作推测」原则一致：近似匹配必须显式暴露，不能伪装成精确命中。

**③ 别名整词化，并把协议显式化**
现在是 `" ".join(...)` 然后 `split(' ')`，是隐式协议。改成数据里就是**数组**：
```json
"aliases": ["拉力琅", "拉力琅芳"]
```
顺带解决 R5。同时 `aliases.py` 增加两条构建期校验：
- 别名不得与任何学校的 `name` / `short` 完全相等（防 R8）
- 别名不得含空格

**④ 别名外置为数据文件**
把 `ALIASES` 从 Python 常量搬到 `data/aliases.json`：
```json
[
  { "alias": "拉力琅",   "targets": ["琅琊路小学", "拉萨路小学", "力学小学"] },
  { "alias": "玄外",     "targets": ["玄武外国语学校", "玄武外国语学校附属小学"] }
]
```
好处：内容团队能自己补俗称，不用改代码、不用我参与。构建期仍然做「必须命中真实学校」的校验。

### 5.4 交互层

| 改进 | 具体做法 |
|---|---|
| **防抖** | `input` 后 120 ms 再查（输入法合成期跳过） |
| **IME 处理** | `compositionstart` 置 `composing=true`，`compositionend` 后手动触发一次；合成期间不渲染 |
| **建议下拉** | 取前 6 条，`<ul role="listbox">` + ↑↓ + Enter + Esc；`aria-activedescendant` 补齐（对比页 P2-4 同款问题，可一并修） |
| **分页** | 首屏 24 张 + 「加载更多」，与 P0-1 合并做 |
| **空态** | 列出当前生效条件，每条带 × 可单独删；若触发近似匹配，给出「你是不是想搜 XX」 |
| **历史** | `localStorage['nj-recent']` 保留最近 8 所，用于「最近浏览」 |
| **排序切换** | 相关度 / 区 / 校名拼音，三个按钮 |

### 5.5 工程层：把临时脚本变成护栏

**① 测试落仓**

```
tests/
  search.test.mjs      # 直接 import assets/search.js，跑查询断言
  search-cases.json    # 用例表（可被非开发者维护）
```

用例表长这样，一条一个断言：
```json
[
  { "q": "拉力琅",   "expect": 3, "first": "南京市琅琊路小学" },
  { "q": "29中",     "expect": 7, "first": "南京市第二十九中学" },
  { "q": "9中",      "expect": 2, "mustNotContain": "第二十九中学" },
  { "q": "lyl",      "expect": 3 },
  { "q": "琅玡路",   "expect": 5, "mode": "fuzzy" }
]
```
第一批我实测的 17 个查询就是这份用例表的雏形，现在只是散落在 `/tmp` 里。**把它固化下来，是这次优化里性价比最高的一件事。**

**② `check.py` 增加三条守卫**

| 守卫 | 防的问题 |
|---|---|
| `cols` 与 `rows[i]` 长度一致，且无 `None` 出现在可搜索列 | R7 |
| 别名不与校名/简称冲突 | R8 |
| `schools-data.js` 体积预算（现值 197 KB，超 240 KB 报警） | 索引膨胀 |

**③ 三处入口收敛为一处**

`home.html` 的 `onkeydown` / `404.html` 的 `nfGo()` / `schools.html` 的搜索，全部改为：
```html
<form role="search" action="schools.html" method="get"><input name="q"></form>
```
JS 只做增强（建议、防抖），不承担「能不能用」。**这样 JS 挂了搜索依然可用**——顺带解决 P1-6 和 P1-7 的一半。

## 6. 分阶段实施

| 期 | 内容 | 交付物 | 验收标准 |
|---|---|---|---|
| **一 · 地基**（1 天） | 搜索抽成 `assets/search.js`；别名外置 JSON + 数组化；测试落仓；check 三条守卫；三处入口收敛为表单 | 可单测的模块 + 20 条用例 | `node --test` 全绿；`make site` 0 错 0 警；现有 17 个查询结果与今天完全一致（**先锁住行为，再改行为**） |
| **二 · 召回**（2–3 天） | 拼音全拼 + 首字母；多音字覆盖表；容错（零结果才启用，显式标注） | `data/pinyin_map.json` + 用例扩到 40 条 | `lyl`/`langya`/`琅玡路` 均能命中；误命中率不升（用现有 17 条对照） |
| **三 · 交互**（2–3 天） | 防抖 + IME + 建议下拉 + 分页 + 空态逐项可删 + 排序切换 | `assets/search-ui.js` | 输入法合成期无闪烁；首屏 24 张（与 P0-1 合并验收） |
| **四 · 收尾** | 搜索历史/最近浏览；章节标题入索引；多面查询语法 | — | 可选，按需 |

**必须遵守的顺序**：一期**只做重构、不改行为**。用例先把今天的结果钉死，二期起每改一处都能立刻知道「哪些旧行为被改动了」。第一批踩过的「容错匹配把 4 所学校错配」就是没有这层护栏的后果。

## 7. 风险与取舍

| 风险 | 应对 |
|---|---|
| **拼音引入新的误命中**（`lyl` 可能同时是「琅琊路」和别的） | 首字母用整词相等而非子串；零结果才回落到前缀 |
| **容错让错配回归** | 只在零结果时启用；必须显式标注「近似结果」；编辑距离阈值 1、词长 ≥ 3 |
| **别名表变成无人维护的死数据** | 外置 JSON + 构建期校验；`docs/` 里写清「怎么加一条别名」，两分钟能学会 |
| **抽模块后模板 include 失效** | 改为 `<script src="assets/search.js">`，与 `schools-data.js` 同目录，路径与缓存一并解决（顺带完成 P2-2） |
| **多音字覆盖不全** | 只影响拼音通道，不影响中文检索；错了可以后续单条修，属于可增量修复的风险 |
