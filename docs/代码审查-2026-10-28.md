# 代码审查报告

> 日期：2026-10-28（含 10-28 下午的一次自我更正）
> 范围：南京中小学档案站（558 页静态站）的 Python 构建管线、前端脚本、模板、工程结构与质量门禁
> 方法：`/usr/bin/time` 实测 + `builtins.open` 插桩 + 变异测试（故意制造缺陷看门禁是否拦截）+ 静态扫描
> **本次只审查，未修改任何业务代码**

## 0. 先更正我自己的一处错误

第一版报告我写「构建耗时 107 秒，CPU 只占 9 秒，93% 时间在等 I/O」，并据此把「合并重复读取」列为 P0-1，预期收益「107s → 60s」。

**这个结论是错的。** 107 秒是我所在执行环境的假象：

- 我的 shell 里 `PYTHONPATH` 指向 `/Applications/WorkBuddy.app/.../cli/vendor/shim`
- 那里的 `sitecustomize.py` 把 `builtins.open` 换成了经 socket 转发的代理，**每次 open 都要往返一次**
- 实测同一批 40 个 md：带 shim **54.2ms/次**，`env -u PYTHONPATH` 下 **0.15ms/次**（差约 360 倍），且延迟与文件大小无关

**去掉 shim 后真实构建：7.72 秒 / 558 页 / 0 错误 0 警告。** 12ms/页——构建性能根本不是问题。

所以「读三遍」这条依然成立（1640 次 / 冗余 1090 次，独立插桩两次结果一致），但它的性能收益是 **0.16 秒**，不是 60 秒。它降级为**正确性问题**（三处各自假设、`_md_text(_cache={})` 会跨构建串味），优先级下调到「下一轮」。

> 教训：**在没有对照组的性能测量上，measurement artifact 和真实瓶颈长得一模一样。** 任何「慢了 N 倍」的结论，都必须先排除执行环境注入。

## 1. 一句话结论

**代码质量本身不差，问题出在质量保障链路上：门禁没在跑，而门禁自己还有洞。**

管线内部干净得超出预期——0 处 `except Exception`、pipeline 内 0 处硬编码路径、每个模块的 docstring 都在解释「为什么」。但：

- CI 从第一步就是断的（**这道门禁只存在于本机**）
- 即便在本机能跑，它也会**放行「学校库整页白屏」**
- 公开页面上有一个数字**低报了 35 所**，而这正是这个站最不能错的地方

## 3. P0 · 立刻做（三条都是「错误可能被发布出去」的路径）

### P0-1 `about` 页的官网覆盖率低报 35 所

**位置**：`site/about.html`（由 `templates/about.html` + `data/school_websites.json` 的 `counts` 字段渲染）

**问题**
页面写「**(153) 所（28%）已核实到可用官网**」。而 `data/school_websites.json` 里 `schools` 有 545 条记录，现算「`site` 非空且 `site_state == ok`」是 **188 所（34.5%）**。

```
缓存 counts： total=229, with_site=153, ok=153
实际 records：545 条，其中 ok=188
差额：+35 所
```

**为什么这是问题**
`counts` 是**手写缓存**，只有联网跑的 `merge_websites.py` 会重算它；后续 8 个 `add_websites_*.py` 补录脚本一个都不更新它，于是它冻结在 10-22 的状态（229 / 153）。

这个站的立身之本是「查不到就写未获取」。一个 `json.load` 就能推翻的数字挂在公开页面上，比漏一百个字段更伤——**它让站点对自己的覆盖率低报了 35 所**，而且方向是「把自己说得更差」，看起来像数据没做完。

**改法**
删掉 `counts` 字段，构建期从 `schools` 现算（`render.about()` 里 2 行）；在 `check.py` 加一条守卫：`counts` 若存在且与现算不符则报错。

**预期收益**：页面数字与数据一致；今后补录官网不再需要记得手动更新缓存。

**成本**：小，约 20 分钟。

### P0-2 CI 从未成功运行过

**位置**：`.github/workflows/build.yml`；`src/build_index.py:11`；`.gitignore:9`

**问题**
三个独立死因，任一个都足以让 CI 在全新 clone 上失败：

1. **第一步就崩**：`build.yml` 第 3 步跑 `python src/validate.py`，它 `from pipeline import load` → `load.load_index()` 读 `index.json`；而 `index.json` 在 `.gitignore` 里（`git ls-files index.json` = 0 条）。全新 clone 上该文件不存在 → `FileNotFoundError`。
2. **顺序反了**：真正生成 `index.json` 的 `python src/build_index.py` 排在 validate **之后**，即使文件不存在也轮不到它先跑。
3. **路径写死**：`src/build_index.py:11` `ROOT = "/Users/kongc/WorkBuddy/南京学校"`。在 ubuntu runner 上这个目录不存在，545 条记录全部进 `skipped`，写出一份空索引。另有 8 个同类脚本（`build_catalog.py` / `build_xlsx.py` / `audit_data.py` / `verify_websites.py` / `reconcile.py` / `merge_websites.py` / `fix_sources.py` / `build_sources.py`）也都是硬编码。

`link-check.yml` 用同一套硬编码路径，同样没在跑。

**为什么这是问题**
**「0 错误 0 警告」这道门禁，实际上只在你本机的 `make` 里存在。** 一旦忘了本地跑就推送，没有任何自动化会拦。这比「门禁有洞」更根本——门禁压根没上岗。

**改法**
- `ROOT` 改为 `Path(__file__).resolve().parents[1]`（9 个文件，各 1 行）
- `build.yml` 调整步骤顺序：先 `build_index.py`，再 `validate.py`
- 补 `requirements.txt`（本地 markdown 3.11.2；CI 装最新版，而 `mdtext` 依赖 `toc_tokens` 结构，版本漂移会静默改变产物）

**预期收益**：CI 从「必挂」变成「可用」；推送即验证，不再依赖人记得跑。

**成本**：小，约 40 分钟（含一次手动触发验证）。

### P0-3 门禁放行「学校库整页白屏」

**位置**：`assets/schools.js:7 / :165`、`src/pipeline/check.py`（缺校验）

**问题**
变异测试：把 `site/assets/schools-data.js` 里的 `districts` 键删掉（模拟一次生成缺陷），然后跑门禁：

```
门禁结果：错误 0 / 警告 0     ← 放行
```

而浏览器里的真实后果：

- `schools.js:7` `const ALL_DISTRICTS = window.__SCHOOLS__.districts;` → `undefined`
- `schools.js:165` `chips('f-dist', 'dist', ALL_DISTRICTS, '全部区')`
- `chips()` 第 2 行 `values.map(...)` → **`TypeError`，抛在模块顶层**
- 之后所有代码（筛选接线、`render()`、骨架屏替换）**全部不执行**
- 结果：6 个骨架块永久停留，页面等于白屏

同类洞还有两个：

| 洞 | 后果 | 门禁 |
|---|---|---|
| `districts` 缺失 | 学校库白屏 | 0 错误 |
| `factLabels` 缺失 | 对比页标签全 `undefined` | 0 错误（`check.py:216` 写的是 `if clabels and …`，标签表为空时整段校验被跳过） |
| `check.py:265` `subprocess.run(..., text=True)` 未指定 `encoding` | 数据文件含非法 UTF-8 时**门禁自己抛 `UnicodeDecodeError` 崩掉**（已复现） | 门禁崩溃 |

**为什么这是问题**
门禁的价值是「拦住会坏的东西」。前两个洞的共同特征是：**校验逻辑以「数据存在」为前提，而缺陷恰恰是「数据不存在」**——最该拦的场景自动跳过。

**改法**
- `check.py` 增加「产物结构完整性」校验：`schools-data.js` 必须含 `cols/rows/districts` 且 `districts` 非空；`compare` 数据必须含 `factLabels` 且非空
- `subprocess.run` 补 `encoding="utf-8"`
- 把上面三条变异写成 `tests/test_check.py`（喂坏产物，断言会报错），让门禁首次拥有测试

**预期收益**：白屏级故障从「静默放行」变成「构建失败」；门禁从 0 测试变成可回归。

**成本**：小，约 1 小时。

## 4. P1 · 下一轮

### P1-1 同一批档案被读三遍（正确性问题，不是性能问题）

**位置**：`schema.py:115`、`load.py:94`、`render.py:124`

**问题**
545 份档案被三个地方各读一次（1640 次读取 / 冗余 1090）。三处互不知道对方读过：
- `schema.validate_schools` 为了查「数据缺口」章节去读全文——**校验层在做 I/O**
- `load.load_body` 渲染详情页时读
- `render._md_text` 生成 `schools-data.js` 时读，自带 `_cache={}` 可变默认参数

**为什么这是问题**
性能上只值 0.16 秒（见第 0 节）。真正的问题是：
1. 校验层本该只判断数据结构，却在打开文件——它的失败原因会混入 I/O 错误
2. `_md_text(_cache={})` 是跨调用共享的全局缓存，进程内多次构建会串味
3. 三处各自假设文本已加载，改一处容易漏另两处

**改法**：`load.py` 建唯一缓存入口 `source_text(school)`，三处共用；`validate_schools` 改为接收已加载文本。

**预期收益**：校验层变纯函数、可单测；读取次数 1640 → 545；消除跨构建缓存污染。

**成本**：小，约 1 小时。

### P1-2 `src/` 里死代码是活代码的 13 倍

**位置**：`src/` 根目录

**问题**：82 个脚本、28633 行，与 `src/pipeline/`（11 文件、2140 行）平级。

| 前缀 | 数量 | 性质 |
|---|---|---|
| `gen_*` | 40 | 历史批量生成 |
| `append_index_*` | 14 | 历史批量写索引 |
| `add_websites_*` | 8 | 历史批量补官网 |
| `report_* / parse_* / fix_*` | 6 | 一次性分析 |
| `build_*` | 5 | **仍在用**（含 `build_index.py`） |
| `audit_ / verify_ / reconcile / merge_ / validate / junior_override` | 9 | 审计与运维工具 |

**为什么这是问题**：61/82 是一键跑完就作废的补录脚本，却和活工具平级。我在审查时第一眼误判成「全是死代码」，其实 `build_index.py` 是生成索引的关键工具——**连审查者都要翻一遍才分得清，就是结构问题**。

**改法**：`gen_* / append_index_* / add_websites_* / report_* / parse_*` 移入 `scripts/archive/`；`build_* / verify_* / audit_*` 移入 `scripts/tools/` 并在 README 写明用途；`src/` 只留 `pipeline/`。

**预期收益**：新人/AI 不再误读；`git grep` 噪声大幅下降。**零风险**（pipeline 不 import 它们）。

**成本**：小，约 30 分钟。

### P1-3 `check.py:run()` 322 行、`main.py:run()` 133 行

**问题**：`check.run()` 一个函数里铺了 20+ 项检查；`main.run()` 把读取→校验→渲染→写入→检查五阶段写在一个函数体。

**为什么是问题**：加一项检查要在大函数里找位置插入；无法单独测试某一项（这正是 check.py 零测试的原因）；`main.run()` 不能只跑「检查」。

**改法**：`check.py` 拆成 `check_links / check_assets / check_pages / check_templates`，各自返回 `Report` 片段；`main.py` 拆成五个 stage 函数。

**预期收益**：检查项可单测；`make check` 可独立运行。行为不变，可用现有 0 错 0 警作回归基线。

**成本**：中，约 3 小时，纯重构。

### P1-4 模板里「四条硬规则」抄了 5 份

**位置**：`talent.html` + 4 个分类页

**为什么是问题**：规则一改要同步 5 个文件，漏一个就前后矛盾——而这个站的核心卖点正是前后一致。

**改法**：`talent_shared.html` 增加 `hard_rules()` 与 `eligibility_gate()` 两个宏。

**预期收益**：规则单点维护；模板总量减约 120 行。**成本**：小，约 40 分钟。

### P1-6 模板与数据文件「双真相」

**问题**：`data/talent_schools.json` 有 49 条 `plan`（如 `"125 人"`），模板正文里另有 **39 处手写人数**（如「软件工程 5 人 + 人工智能 120 人」）。同一事实写两遍，互不校验。

**为什么是问题**：改一处漏一处就出现「表格说 125 人、正文说 5+120」这种自相矛盾；而 `plan` 还是自由文本，无法排序/求和/校验。

**改法**：正文中的人数改为模板变量引用 json；`plan` 拆成 `plan_n`（整数）+ `plan_note`。

**成本**：中。

### P1-7 11 处 `open()` 未用 `with`
