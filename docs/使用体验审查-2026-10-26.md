# 南京中小学档案 · 使用体验审查报告

> 审查日期：2026-10-26
> 审查对象：已构建站点 `site/`，共 **552 页**（545 个学校详情页 + 7 个功能页）
> 审查方式：全部结论来自**实测**（`grep` 全量扫描 + Node 脚本跑 `schools-data.js` + 模板/样式的逐条规则比对），不含主观判断
> 范围限定：按你的要求，**不涉及上线**，只看使用层面

---

## 摘要

**数据底子很扎实，交互层是短板。**

545 所学校、16 张应收清单全部归零、表格窄屏适配 100% 覆盖、信度标注成体系——这些是硬功夫。
但一个真实家长打开这个站点，最可能发生的三件事是：

1. 想搜「拉力琅」，**搜出 0 条**（P0-2）
2. 打开学校库，**先等 195 KB 数据解析完**，期间页面一片空白（P0-1）
3. 读完一所学校的档案，**没有任何出口**，只能浏览器后退（P1-2）

问题总数 **17 项**：P0 阻断级 5 项、P1 明显影响 8 项、P2 打磨级 5 项（含 1 项重复计入）。
其中 **P0-4 是删两行代码的事，P0-3 是加五行的事**——修复成本与收益严重不成比例，建议先做。

## 二、P0 阻断级（5 项）

### P0-1 学校库 545 张卡片一次性渲染

**位置**　`templates/schools.html#grid` + `templates/schools.js:95-109`

**实测证据**

```js
grid.innerHTML = rows.map(function (s) { ... }).join('');   // 全量，无 slice、无分页
```

- 默认进入是「全部学段 / 全部区」→ **545 张卡片**，每张 7–9 个节点，一次性约 **4000+ DOM 节点**
- `schools-data.js` **195.4 KB**（gzip 50.8 KB），且是 **JS 对象字面量**（`window.__SCHOOLS__ = {...}`），要靠 JS 引擎解析 545 行数组，比 `JSON.parse` 慢 2–3 倍
- 数据下载 + 解析完成前，`#grid` 是空的，**没有骨架屏、没有加载提示**

**影响**
中低端安卓机上首屏可见内容迟迟不出现，用户看到的是一个「只有标题、下面全白」的页面——很像坏了。
数据到了以后又有一次约 4000 节点的同步 DOM 插入，会造成一次明显卡顿；之后滚动长列表也容易掉帧。

**优化方案**（按投入产出排序）

1. **首屏只渲染 24 张** + 底部「加载更多」按钮（或 IntersectionObserver 滚到底自动追加）——改动最小，收益最大
2. `state` 变化时不要 `innerHTML` 全量重建，改为按 key 做增删（可先用简单的「只重建当前页」过渡）
3. 构建期把 `schools-data.js` 输出成 `window.__SCHOOLS__ = JSON.parse('...')` 或独立 `.json` + `fetch`，解析成本直接减半以上
4. 加骨架屏（6 个灰色 `.card` 占位，CSS 就可实现）

**预期收益**　首屏可见内容出现时间主要取决于「24 张卡片渲染完」而非「195 KB 解析完」，实测下预计下降 60%+；同步 DOM 插入从 4000 节点降到 200 以内，卡顿消失。

**优先级**　**立即（P0）**

### P0-2 搜索是字面子串匹配，家长的说法搜不到

**位置**　`templates/schools.js:40-42`（分词）、`:74-78`（匹配）

**实测证据**（用 Node 直接跑 `schools-data.js`，与线上逻辑一致）

```js
const hay = (s.name + ' ' + s.short + ' ' + s.tier + ' ' + s.tagline + ' ' + s.district).toLowerCase();
if (!ts.every(t => hay.indexOf(t) !== -1)) return false;   // 纯字面子串
```

| 搜索词 | 实际命中 | 问题 |
|---|---|---|
| **拉力琅** | **0 条** | 家长圈最常用的三校合称，一条都搜不到 |
| 琅琊路 | 6 条 | 混入了无关学校（tagline 里提到） |
| 二十九中 | 13 条 | **误命中琅小/拉小/力学**，只因 tagline 提了一句 |
| 附中 | 39 条 | tagline 里的泛词把结果撑满 |
| 施教区 | 189 条 | 同上，噪声源 |
| 集团 | 70 条 | 同上 |
| 江北 | 95 条 | 因为 `district` 值是「江北新区」，属可接受 |

**影响**
这是全站**最致命的一环**。用户不会用官方全名搜，他用的是「拉力琅」「玄外」「二十九中」「金中」。
搜不到 → 用户判断「这网站没收这所学校」→ 直接关掉，**没有任何补救机会**。
反过来，搜「二十九中」却跳出琅小、拉小、力学，用户会怀疑数据准确性——这会伤到最不该伤的东西：**可信度**。

**优化方案**

1. **加 `aliases` 字段**，构建期并入搜索索引：拉力琅→琅琊路/拉萨路/力学；玄外→玄武外国语；金中→金陵中学；南师附中→南师附中/附中；游小→游府西街小学……（这批词表本身很有价值，建议单独存 `data/aliases.yaml`）
2. **`tagline` 退出搜索索引**。它是叙述性长文本，是噪声的唯一来源。只搜 `name / short / aliases / tier / district` 五个字段
3. 加**拼音首字母**（`lyl` → 琅琊路）与**错字容错**（Levenshtein ≤ 1，只对 2 字以上的词启用）
4. **按字段权重排序**：校名完全匹配 > 校名包含 > 简称/别名 > 区县 > 梯队
5. 搜索框下拉给**实时建议**（前 6 条），而不是只改网格

**预期收益**　常用简称命中率从约 50% 提到 95% 以上；误命中（二十九中→琅小）清零；这是 17 项里**投入产出比最高的一项**，且纯前端改动、不依赖数据补录。

**优先级**　**立即（P0）**

### P0-3 深色模式每次翻页闪白

**位置**　`templates/base.html`（`<head>` 里只有一行加 `js` class 的脚本，**没有**主题脚本）+ `site/assets/app.js:9-46`

**实测证据**

```html
<!-- base.html 结尾 -->
<script src="{{ base }}assets/app.js"></script>   <!-- 在 </body> 前 -->
```

```js
// app.js 第 17-18 行
var saved = read();
if (saved) document.documentElement.setAttribute('data-theme', saved);
```

`app.js` 在 `</body>` 前才加载，执行到这行时页面**已经完成首次绘制**。

**影响**
选了深色模式的用户，在站内每点一次链接就闪一次白。读 545 个档案、来回跳转几十次，就是闪几十次白。
更糟的是心理预期：用户会以为「主题没保存住」，下次干脆不点了。

**优化方案**
在 `<head>` **最前面**（`<meta charset>` 之后）插入内联脚本：

```html
<script>try{var t=localStorage.getItem('nj-theme');if(t)document.documentElement.setAttribute('data-theme',t)}catch(e){}</script>
```

`app.js` 里只保留切换与图标绘制逻辑，删掉第 17–18 行的设置。

**预期收益**　翻页闪白 100% 消除；改动 5 行、零风险。

**优先级**　**立即（P0）**

### P0-4 `pages.css` / `responsive.css` 各被加载两次

**位置**　`templates/base.html:26-29`

**实测证据**

```html
<link rel="stylesheet" href="{{ base }}assets/pages.css">      <!-- 26 -->
<link rel="stylesheet" href="{{ base }}assets/responsive.css"> <!-- 27 -->
<link rel="stylesheet" href="{{ base }}assets/pages.css">      <!-- 28 重复 -->
<link rel="stylesheet" href="{{ base }}assets/responsive.css"> <!-- 29 重复 -->
```

**影响**
- 表面：每次开页面多 2 个请求（HTTP/1.1 下多 2 个 RTT），浏览器重复解析 22.1 KB CSS
- 真正麻烦的是**层叠顺序被打乱**。`responsive.css` 头部注释明确写着「必须最后加载」，现在 `pages.css` 在它之后又插了一次——将来调断点覆盖时会出现「明明写在 responsive 里却不生效」，而这正是此前踩过的坑（见 `responsive.css` 第 4 行注释）

**优化方案**　删掉第 28、29 两行。同时建议在 `check.py` 里加一条守卫：同一 `href` 只允许出现一次。

**预期收益**　省 2 个请求 / 22.1 KB；消除一个必然会再踩的调试陷阱。

**优先级**　**立即（P0，一行修复）**

552 个页面 → 542 个唯一 title → 重复 10 组（均为小学部/初中部同名）

**优先级**　**立即（P0）**

## 三、P1 明显影响效率（8 项）

### P1-1 详情页目录在 ≤1023px 直接消失

**位置**　`site/assets/responsive.css:20` `.toc{display:none}`

**影响**
最大的详情页正文 **51.4 KB、10 个 `<h2>`、18 张表、58 段**。平板和手机上读这样的页面，目录没了，只能盲滚——**而移动端恰恰是最需要目录的场景**。
现有注释说「正文各章节标题本身足以导航」，这在 3 屏的短档案上成立，在 92 KB 的长档案上不成立。

**优化方案**（三选一，按成本排序）
1. 顶部做成 **sticky 横向滚动条**：`overflow-x:auto; white-space:nowrap`，只显示「章节序号 + 4 字短标题」
2. 吸顶一条「本页目录 ▾」，点击展开全屏抽屉
3. 退化成 `<select>`「跳到章节」

**预期收益**　长页面定位从「滚 20 屏」变成「点一次」。

**优先级**　高

### P1-2 详情页没有出口：无上一所/下一所/相关学校

**位置**　`templates/detail.html`（`</article>` 之后到 `{% endblock %}` 之间是空的）

**影响**
读完一所学校，想对比同区另一所，当前路径是：
`浏览器后退 → 学校库 → 重新选筛选项 → 找到目标 → 点进去`，**4 步换 1 步**。
详情页是 545 个独立入口，但每一个都是**死胡同**。跳出率会很高，而站内其实已经做好了 `compare.html` 的 2–4 校对比能力，**却没有任何入口从详情页进去**——这是最大的浪费。

**优化方案**　页尾加三块：
1. **上一所 / 下一所**：按 `index.json` 的名录顺序（同区同学段），一行两个链接
2. **同区其他学校**：4–6 个卡片，复用 `partials.html` 的 `card()` macro
3. **「加入对比」按钮**：写 `localStorage['nj-compare']`，跳 `compare.html` ——**这一项价值最高**，把已有能力接进主流程

**预期收益**　站内浏览深度提升；对比功能从「藏着的功能」变成「主路径的一部分」。

**优先级**　高

### P1-3 面包屑不是导航语义，也没有结构化数据

**位置**　`templates/detail.html:6-9`

```html
<div class="crumb"><a>首页</a> / <a>学校库</a> / <a>小学</a> / <a>鼓楼</a></div>
```

**影响**
- 屏幕阅读器不会把它识别为导航区域，用户跳不到
- 分隔符 `/` 是纯文本，键盘 Tab 过去是 4 个孤立链接，没有层级关系
- 552 页都缺 `BreadcrumbList`，搜索引擎少了一层可见性

**优化方案**

```html
<nav aria-label="面包屑"><ol><li><a>首页</a></li><li><a>学校库</a></li>…</ol></nav>
```

分隔符改 CSS `li + li::before{content:"/"}`；JSON-LD 里补 `BreadcrumbList`。

**预期收益**　无障碍与 SEO 双收益，改动集中在 1 个模板。

**优先级**　高

### P1-4 全站 0/552 张 `og:image`

**位置**　`templates/base.html`（有 `og:site_name` / `og:title` / `og:description` / `og:url`，**唯独没有 image**）。实测 `grep -l "og:image"` → **0**

**影响**
在微信、群里分享一条学校档案，出来是一个**光秃秃的灰字链接**，没有缩略图。同样内容有图的卡片，点击率差距是数量级的。这个站的传播主要靠家长群，这条影响很直接。

**优化方案**
1. 生成 1 张站级默认图 1200×630（用现有 tokens 配色，标题「南京中小学档案」+ 545 所）
2. 再按 11 个区 + 3 个学段出 14 张模板图（构建期 SVG → PNG，纯脚本可做）
3. `og:image` 指向对应区图，补 `og:image:width/height` 与 `twitter:card=summary_large_image`
4. 注意：详情页 `base` 是 `../`，`og:image` **必须是绝对 URL**，否则微信抓不到

**预期收益**　分享卡片从无图变有图，传播转化提升。

**优先级**　中高

### P1-5 键盘焦点被覆盖；`.chip` 触控区偏小

**位置**　`site/assets/site.css:37` vs `:85-95`

**实测证据**

```css
/* 37 行：全局键盘焦点 */
:focus-visible{outline:2px solid var(--accent);outline-offset:2px;border-radius:var(--r-sm)}

/* 85 行：搜索框基础规则 */
#q, .picker input { ... outline:none; ... }
/* 87 行：只给了 box-shadow */
#q:focus,.picker input:focus{border-color:var(--accent);box-shadow:0 0 0 4px var(--accent-weak)}

/* 91 行 */
.chip{ ... min-height:36px; ... }
/* responsive.css:58 —— 移动端 38px */
.chip{min-height:38px;padding:8px 14px;font-size:var(--f-sm)}
```

`#q` 的 ID 选择器优先级高于全局 `:focus-visible`，所以**输入框键盘聚焦时拿不到那圈 outline**，只剩一圈淡阴影，深色模式下更弱。
`.chip` 桌面 36px、移动 38px，均低于 Apple HIG 的 44px 与 WCAG 2.5.5（AAA）。它们是全站点击频率最高的元素。

**优化方案**
1. `#q` 基础规则删掉 `outline:none`，只保留 `:focus` 的 box-shadow
2. 补 `#q:focus-visible{outline:2px solid var(--accent);outline-offset:2px}`
3. `.chip` 提到 `min-height:44px`（移动端 44，桌面可折中 40）

**预期收益**　键盘可用性达标；手指点偏率下降（筛选项密集时尤其明显）。

**优先级**　中高

### P1-6 首页搜索不是表单

**位置**　`templates/home.html:9-14`

```html
<input id="hq" onkeydown="if(event.key==='Enter')heroSearch()">
<button type="button" onclick="heroSearch()">搜索</button>
```

**影响**
1. 不是 `<form role="search">`，回车靠手写 keydown 撑，**JS 一挂就完全失效**
2. 没有 `autofocus`，进站要多点一下
3. 空着搜索框，用户不知道该搜什么。placeholder 举了「琅琊路」「金中」「江北」——但按 P0-2 的实测，「琅琊路」会带出 6 条含噪声的结果，「江北」会出 95 条，**示例词本身就不够准**

**优化方案**
1. 改真表单：`<form role="search" action="schools.html" method="get"><input name="q">`，JS 只做增强
2. 加 `/` 聚焦快捷键（`keydown` 判断不在输入框内且 `e.key==='/'`）
3. 搜索框下方放「热门：拉力琅 / 玄外 / 二十九中 / 鼓楼 / 民办」快捷 chip，点击直达
4. placeholder 换成实测能精准命中的词

**预期收益**　搜索入口可用性 + 引导性提升；顺带把 P0-2 的别名表价值放大。

**优先级**　中

### P1-7 全站 0 处 `<noscript>`，关 JS 后一所学校都看不到

**位置**　`templates/schools.html`（`<div id="grid"></div>` 初始为空，全部由 JS 注入）。实测 `grep -c noscript templates/*.html` → **全为 0**

**影响**
- JS 失败、被拦截、或被企业浏览器策略禁用时，学校库页面上**一条学校链接都没有**——545 个最重要的入口集体消失
- 对搜索引擎：详情页虽在 sitemap 里，但站内**没有任何静态链接指向它们**，拿不到内链权重

**优化方案**
构建期把 545 所学校按「区 → 学段」输出成静态 `<ul>`，默认可见；JS 接管后隐藏静态列表、切到筛选视图。
最低成本的兜底：至少在 `<noscript>` 里输出「按区 / 按学段」的静态入口链接。

**预期收益**　可用性兜底 + 站内链接结构被完整抓取。

**优先级**　中

### P1-8 筛选状态不写回 URL

**位置**　`templates/schools.js:13`（只**读** `?q=`，从不写）+ `templates/schools.html:30-43`（只处理 `?lv=` / `?dist=`，**`?type=` 缺失**）

**影响**
- 搜到满意的结果想发到群里，复制出来的 URL 是光秃秃的 `schools.html`，对方看到的是全量 545 所
- 按浏览器后退键，**直接离开页面**，而不是回到上一组筛选条件
- `?type=民办` 这种链接点击无效，与 `?lv=` / `?dist=` 行为不一致

**优化方案**
1. `render()` 末尾 `history.replaceState` 同步 `q/lv/dist/type` 四参
2. 筛选变化时 `pushState`；监听 `popstate` 还原 `state` 并重绘
3. 补 `?type=` 分支，与另外两个保持一致

**预期收益**　可分享、可后退，符合直觉；`compare.html?ids=` 已经是这么做的，风格统一。

**优先级**　中

## 四、P2 打磨级（5 项）

### P2-1 详情页体积偏大

**实测**　545 页共 **20.0 MB**，平均 **36 KB**，最大 `小学-南京江北新区外国语小学.html` **92.3 KB**（正文 51.4 KB / 10 个 h2 / 18 张表 / 58 段）

**影响**　单页 HTML 越大，DOM 构建越慢。文本未压缩（服务器开 gzip 可降约 70%，但这不是代码层能保证的）。

**方案**　构建期做 HTML 压缩（去行首缩进、去注释）；长档案把「数据缺口清单」这类低价值长表默认装进 `<details>`。

**预期收益**　压缩后单页传输体积降 20–30%。

**优先级**　低

---

### P2-2 内联脚本无法缓存

**位置**　`templates/schools.html:29` `<script>{% include "schools.js" %}</script>`；`compare.html` 同

**影响**　每次进学校库都要重下 5.5 KB（无法 304）；内联脚本也让将来上 CSP 变复杂。

**方案**　抽成 `assets/schools.js` / `assets/compare.js`，带内容 hash 或长缓存头。

**优先级**　低

---

### P2-3 空态只说「没结果」，不说「为什么」

**位置**　`templates/schools.js:86-93`

**影响**　搜不到 → 点「清除全部筛选」→ 卡片回来了，但用户**不知道自己刚才是被哪一项挡住的**，下次还会犯同样的错。窄屏下筛选区本身是折叠的，更难自查。

**方案**　空态里直接列出当前生效条件，每条带 × 可单独移除：`搜索「拉力琅」×` `小学 ×` `鼓楼 ×`。

**预期收益**　用户能自己定位问题，不用猜。

**优先级**　低

---

### P2-4 对比页 listbox 缺键盘交互

**位置**　`templates/compare.html` / `compare.js`

**影响**　声明了 `role="listbox"` + `role="option"`，却没有 `aria-activedescendant`、没有 ↑↓、没有 Esc。屏幕阅读器用户会「以为能用键盘，但按了没反应」——**这比不声明角色更糟**。

**方案**　补齐 ↑↓ 移动 + Enter 选中 + Esc 收起 + `aria-activedescendant`；或干脆去掉 listbox 角色，改为普通按钮组。

**优先级**　低

---

### P2-5 全站无「回到顶部」

**影响**　92 KB 的长档案滚到底部想回目录，只能一路手滚。

**方案**　滚动超过 1.5 屏后右下角浮出「↑ 回顶部」，详情页版本再加「↑ 回目录」。

**优先级**　低

## 七、本次审查确认「做对了，不要改」的地方

写这份报告时顺手验证的，以下各项**质量在线，改造时务必保留**：

1. **表格 `data-label` 覆盖 539/539 = 100%** ——窄屏卡片化表格这块是全站质量最高的部分，没有一处遗漏
2. **搜索高亮的转义顺序正确**（`schools.js:24-37`）：**先 `esc()` 再包 `<mark>`**，用户输入不会被当 HTML 执行，没有 XSS 口子
